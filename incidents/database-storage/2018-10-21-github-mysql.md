# GitHub 数据库事件（2018-10-21）：43 秒网络分区换来 24 小时降级

## 摘要

2018 年 10 月 21 日 22:52 UTC，一次例行的光纤设备维护导致 GitHub 美国东海岸网络枢纽与东海岸数据中心之间出现 **43 秒**的连接中断。这短暂分区期间，MySQL 高可用编排系统 Orchestrator 依据其共识协议将写主库故障转移到美国**西海岸**数据中心；分区恢复后，东海岸原主库上存在**少量未复制到西海岸的写入**，两侧数据出现分叉（脑裂）。为保证数据一致性，GitHub 主动将服务置于降级状态（暂停 Webhook、Pages 构建，网站部分功能受限），进行长达 24 小时的数据回填、校验与修复，最终于 10 月 22 日 23:00 UTC 恢复全部服务。官方复盘以罕见的深度剖析了"自动故障转移在跨地域拓扑下的边界条件"。

## 影响评估（CRE 视角）

- **影响面**：GitHub.com 全球用户，持续 24h05m 的功能降级（非完全中断）
- **功能维度**：代码读取/克隆基本可用；Issue/PR 等数据库写入受损或延迟；Webhook 投递与 Pages 构建暂停并积压（恢复后重放约 20 万+ 事件）；显示的数据存在陈旧
- **影响时长**：22:52 UTC（10/21）– 23:00 UTC（10/22），约 24 小时降级
- **错误预算**：24 小时降级对 99.95% SLO 为数年预算量级（按降级折算）
- **次生影响**：全球 CI/CD 流水线因 Webhook 暂停而停摆；官方选择"一致性优先于可用性"，接受更长的降级时间以保证不丢数据
- **对外沟通评估**：优秀——事发中持续更新，9 天后发布逐分钟级时间线的深度复盘，明确承诺"数据一致性优先"原则
- **定级依据**：核心写路径大范围受损但读路径基本可用、无永久数据丢失，定 SEV-2
- **补充**：最终确认未复制写入通过人工与自动比对全部完成对账，无用户数据丢失

## 技术细节与根因分析（SRE 视角）

### 背景架构

GitHub 元数据存储于多个 MySQL 集群（主写 + 多读副本），由 **Orchestrator + Raft 共识**实现自动故障转移；应用层假设写主库位于低延迟的东海岸。东西海岸间为异步复制，跨洋写延迟约 60ms+。

### 因素三分

- **触发因素（Trigger）**：43 秒的部分网络分区（枢纽↔东海岸数据中心）。
- **根本原因（Root Cause)**：
  1. Orchestrator 的故障转移决策**未感知"跨地域切换的数据丢失窗口与性能后果"**——在异步复制、尚有未传输 binlog 的情况下把主库切到另一海岸；
  2. 高可用拓扑**允许把写主库迁出应用所在地域**，而应用架构并未按跨地域写设计。
- **扩大因素（Aggravating Factors）**：
  1. 两侧均有写入后，回切需要完整的数据对账，恢复时间由"备份恢复+复制追赶"主导；
  2. 多 TB 备份恢复耗时数小时，且期间东海岸副本持续落后；
  3. Webhook/Pages 暂停造成生态级积压，重放本身也需谨慎控制。

- **减轻因素（Mitigating Factor）**：GitHub 降级运行 24 小时而非完全停摆（只读模式）；数据未丢失。

### 5 Whys

```
现象：43 秒网络抖动导致 24 小时全球降级
Why1 → 写主库被切到西海岸，而东海岸残留未复制写入，数据分叉
Why2 → Orchestrator 按"主库不可达"触发自动切换，未校验复制完整性与目标地域
Why3 → 故障转移策略把"可用性"置于"一致性+局部性"之上，边界条件未建模
Why4 → 跨地域拓扑上线时未演练"短暂分区"场景（43 秒恰好落在检测阈值内）
Why5 → 自动化的决策空间大于架构的承受空间
        （系统性原因：自动故障转移的策略约束落后于拓扑演进）
```

## 解决过程

工程师数分钟内识别数据分叉，面临抉择：强行回切东海岸（快、但丢失西海岸新写入）或完整恢复（慢、不丢数据）。GitHub 选择后者：从备份重建东海岸集群、追赶复制、再将未复制的原东海岸写入逐条对账合并（涉及少量冲突人工裁决）。期间刻意维持降级（暂停 Webhook/Pages）防止不一致数据向外扩散。10 月 22 日 23:00 确认一致后全面恢复并重放积压事件。官方后续改进：调整 Orchestrator 配置禁止跨地域主库切换、推进多活（multi-homing）架构、建立更快的备份恢复能力。

## 经验教训

1. 当使用自动故障转移时，必须为自动化设定**与架构能力匹配的约束**（如：禁止将主库切出应用地域、切换前校验复制完整性），自动化的胆量不能大于架构的承受力。
2. 异步复制体系中，任何故障转移都存在**数据丢失窗口**；必须预先定义"可用性 vs 一致性"的决策原则，避免事中临时抉择（GitHub 预设"一致性优先"使决策迅速）。
3. **短暂分区（秒级）是最危险的分区**——刚好触发切换又迅速恢复，制造双主；混沌演练必须覆盖该场景。
4. 恢复时间由"备份恢复速度 + 复制追赶速度"决定，两者都应作为被度量、被演练的能力（官方后续将其列为工程目标）。
5. 暂停外发通道（Webhook）防止污染下游，是降级设计中"宁可慢、不可错"的正确取舍。

## 预防与改进措施

- **预防（Prevent）**：Orchestrator 配置禁止跨地域切换；故障转移前置复制完整性校验（官方）
- **减小爆炸半径（Contain）**：推进 multi-homing/多活架构，使任一地域故障不依赖跨洋切换（官方）
- **快速检测（Detect）**：数据分叉的自动检测与告警（官方方向）
- **快速恢复（Recover）**：以"数小时级恢复多 TB 集群"为目标优化备份恢复与追赶能力（官方）

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 自动故障转移是双刃剑：无地域/完整性约束的自动化把 43 秒故障放大为 24 小时事件 |
