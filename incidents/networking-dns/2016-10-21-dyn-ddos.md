# Dyn DNS DDoS（2016-10-21）：IoT 僵尸网络让半个美国互联网失联

## 摘要

2016 年 10 月 21 日，托管 DNS 服务商 Dyn 的基础设施遭遇三波由 **Mirai 僵尸网络**（由数十万被入侵的 IoT 设备——摄像头、路由器、DVR 组成）发起的大规模 DDoS 攻击。攻击以海量 TCP/UDP 53 端口流量与畸形查询冲击 Dyn 的托管 DNS 平台，叠加全网递归服务器的重试查询形成流量放大。Twitter、GitHub、Netflix、Spotify、Reddit、PayPal 等仅使用 Dyn 单一 DNS 服务商的大量头部网站在美国东海岸及欧洲部分地区间歇性不可达，影响断续持续约 11 小时。该事件成为 IoT 安全与 **DNS 单供应商依赖风险**的分水岭事件。

## 影响评估（CRE 视角）

- **影响面**：美国东海岸为主、波及欧洲部分地区；Dyn 托管 DNS 的大量头部客户域名（Twitter、GitHub、Netflix 等 70+ 知名服务，E4）
- **功能维度**：DNS 解析失败 → 用户侧表现为网站完全无法访问（TTL 过期后缓存失效者受影响最重）
- **影响时长**：三波攻击，11:10–13:20 UTC、15:50–17:00 UTC、20:00 后各一波，间歇性影响合计约 11 小时窗口
- **错误预算**：对受影响客户，DNS 层中断等同全站中断；单供应商客户当日可用性损失以小时计
- **次生影响**：引发对 IoT 设备默认口令、供应链安全的全球监管与行业讨论；"多 DNS 供应商"自此成为头部站点标配
- **对外沟通评估**：良好——攻击当日持续更新状态页，事后发布官方分析摘要
- **定级依据**：多区域、大量头部客户全站级不可达，定 SEV-1

## 技术细节与根因分析（SRE 视角）

### 背景架构

Dyn 为客户提供权威 DNS 托管。权威 DNS 的特性使其天然是高价值攻击面：打掉一家托管商即可同时打掉其全部单栈客户。Mirai 通过扫描弱口令/默认口令入侵 IoT 设备，形成可发起 Tbps 级流量的僵尸网络（此前已攻击 KrebsOnSecurity 与 OVH），且源码在攻击前已公开，出现多个变种。

### 因素三分

- **触发因素（Trigger）**：Mirai 僵尸网络对 Dyn DNS 基础设施的定向 DDoS。
- **根本原因（Root Cause）**：（从可用性工程视角）
  1. 攻击流量规模超出当时 DNS 基础设施的吸收与清洗能力设计边界；
  2. 对客户而言：**单一 DNS 供应商架构**使供应商故障等价于自身全站故障。
- **扩大因素（Aggravating Factors）**：
  1. 递归服务器与客户端在解析失败后的**重试风暴**，官方分析指出重试使实际流量达到正常的 10~20 倍，真实攻击流量被显著放大；
  2. 攻击分多波且模式变化，缓解措施需反复调整；
  3. Mirai 源码公开导致攻击门槛骤降（生态性因素）。

- **减轻因素（Mitigating Factor）**：Dyn 的 DDoS 缓解团队在 11 小时内逐步恢复；事件推动了全球 DNS 基础设施的 DDoS 防护升级。

### 5 Whys

```
现象：大量头部网站在美东数小时无法访问
Why1 → 这些站点的权威 DNS（Dyn）无法响应查询
Why2 → Dyn 基础设施被 Tbps 级 DDoS 流量与畸形查询淹没
Why3 → Mirai 僵尸网络聚合了数十万台弱口令 IoT 设备的带宽
Why4 → （客户侧）受影响站点仅配置 Dyn 单一 DNS 供应商，无解析冗余
Why5 → 行业长期低估权威 DNS 的集中度风险与 IoT 设备的武器化潜力
        （系统性原因：关键基础设施单点 + 生态级安全外部性）
```

## 解决过程

Dyn NOC 检测到攻击后启动 DDoS 应急：流量清洗、Anycast 流量调度、与上游运营商协同过滤。第一波约 2 小时后缓解；第二波攻击面更广，再次造成影响后于约 1 小时余缓解；第三波被既有缓解措施基本吸收。事件期间部分客户（如 Twitter、GitHub 等）临时增加第二 DNS 供应商以恢复解析。事后行业层面：FBI/DHS 介入调查，Mirai 作者后被起诉；头部互联网公司普遍转向双 DNS 供应商架构。

## 经验教训

1. 当域名解析仅依赖单一 DNS 供应商时，该供应商即为**全站单点**——关键业务必须配置**多权威 DNS 供应商**（不同厂商、不同 Anycast 网络），并常态化演练切换。
2. DNS 故障会触发全网递归器与客户端的**重试放大**（本次达 10~20 倍），容量与清洗设计必须计入这一放大系数。
3. 合理设置 **DNS TTL** 是免费的韧性：过短的 TTL 使缓存无法在权威 DNS 故障期间兜底。
4. 防御方的能力边界受**生态安全水位**制约：IoT 弱口令这类外部性风险需通过行业/监管协同治理（本事件直接推动了相关立法讨论）。
5. 对攻击类故障，**分波次、变模式**是常态，缓解方案必须假设攻击者会适应。

## 预防与改进措施

- **预防（Prevent）**：（客户侧）多 DNS 供应商 + 合理 TTL；（行业）IoT 设备强制唯一口令/自动更新
- **减小爆炸半径（Contain）**：Anycast 分散、按区域隔离清洗（Dyn 官方方向）
- **快速检测（Detect）**：攻击特征与畸形查询识别、与上游运营商的联动通道（Dyn 官方方向）
- **快速恢复（Recover）**：客户侧预置备用 DNS 切换 Runbook；供应商侧多波次攻击的持续响应机制

## SRE / CRE / FDE / SA 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 重试风暴把攻击流量放大 10~20 倍——协议层的失败行为设计（退避/缓存）决定故障烈度 |
| CRE | 供应商的故障就是你的故障：单 DNS 供应商的头部站点当日全部陪葬，多供应商自此成为标准架构 |
| FDE | 区分"攻击流量"与"重试放大流量"是本次流量分析的关键，也是所有 DDoS 复盘的必修课 |
| SA（客情危机） | 半个美国互联网失联，Twitter/GitHub/Netflix 等 70+ 服务中断，公众首次直观感受 IoT 安全的破坏力；Dyn 持续更新状态页+官方分析，但单供应商依赖风险成为行业共识 |
| SA（技术危机） | 多 DNS 供应商自此成为标配——客户应配置多权威 DNS（不同厂商/不同 Anycast 网络）并演练切换；重试放大系数（10~20 倍）必须计入容量设计，合理 TTL 是免费韧性 |
