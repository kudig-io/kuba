# 阿里云 11·12（2023-11-12）：认证服务打喷嚏，全球所有 Region 一起感冒

## 摘要

2023 年 11 月 12 日 17:39 起（北京时间），阿里云发生罕见的**全球性服务异常**：云产品控制台、管控 API（OpenAPI）大面积不可用，**影响所有 Region**——国内外用户同时报告钉钉、闲鱼、阿里云盘等大量依赖阿里云的应用异常，"阿里云崩了"登上热搜。官方事后说明将根因指向**访问密钥（AK）服务**：AK 服务在**读取白名单数据时出现异常**，而**异常处理代码存在缺陷**，生成了**不完整的白名单**，导致鉴权请求被错误拒绝——认证失败使所有依赖 AK 鉴权的云产品 API 与控制台连锁不可用。工程师定位后通过**回滚白名单版本并重启应用**恢复服务，17:39 至 19:20 全部恢复，历时约 **2.5 小时**（部分产品略有长尾）。该事件距离 2022-12-18 香港机房故障不到一年，且爆炸半径为**全球所有 Region**——它揭示了云平台最深层的单点：**身份认证服务是全球共享的隐式基座**，其故障能瞬间穿透一切区域隔离设计。值得注意的是，此次故障主要影响管控面（Console/API），已运行的 ECS 实例、网络转发等数据面基本不受影响。

## 影响评估（CRE 视角）

- **影响面**：全球所有 Region 的云产品控制台与 OpenAPI；OSS、RDS 等产品的管控操作；依赖阿里系云服务的 C 端应用（钉钉、闲鱼、阿里云盘等）功能异常
- **影响时长**：约 101~150 分钟（17:39/17:44 起报，19:20 官方宣布恢复，长尾至 19:43）
- **次生影响**：一年内第二次重大故障叠加，公众信任与商誉承压；"云上应用无法登录/上传"影响大量个人与企业用户
- **对外沟通评估**：状态页与公告响应较快（当晚即公布原因概要与恢复时间），但深度技术复盘未公开发布
- **定级依据**：全球性、全产品管控面中断，SEV-1
- 未披露信息：白名单异常的具体触发数据、受影响 API 调用量、详细整改清单

## 技术细节与根因分析（SRE 视角）

### 背景架构

阿里云所有产品的 API 调用与控制台操作依赖统一的访问密钥（AccessKey，AK）认证体系完成签名鉴权。AK 服务是全球共享的基础服务，内部维护白名单等元数据用于鉴权决策。管控面（Console/OpenAPI）强依赖 AK 鉴权；数据面（已运行的 ECS/网络/存储读写路径中不经过管控鉴权的部分）不受直接影响。

### 因素三分

- **触发因素（Trigger）**：AK 服务读取白名单数据时发生异常（数据或依赖异常）。
- **根本原因（Root Cause）**：异常处理代码存在缺陷——读取异常未被正确处理，而是**生成了不完整的白名单并继续生效**，鉴权由"故障时保守放行/维持旧版"变成了"错误拒绝"；即认证系统在异常路径下未做到 fail-static（维持最后已知良好状态）。
- **扩大因素（Aggravating Factors）**：
  1. AK 服务为全球共享架构，错误白名单瞬间传播至所有 Region，区域隔离对它无效；
  2. 管控面全线强依赖单一认证服务，无降级鉴权路径；
  3. 依赖阿里云的消费级应用（钉钉/闲鱼等）同步故障，影响穿透至 C 端。
- **减轻因素（Mitigating Factor）**：数据面基本无损（已运行实例、网络转发正常）；回滚路径明确，恢复较快（101 分钟）。

### 5 Whys

```
现象：全球所有 Region 控制台与 OpenAPI 中断约 2 小时
Why1 → AK 鉴权大面积错误拒绝，管控请求全部失败
Why2 → AK 服务生成并加载了不完整的白名单
Why3 → 白名单读取异常时，异常处理代码缺陷让"半成品"数据生效
Why4 → 认证服务异常路径未实现 fail-static（维持最后已知良好版本），
        异常分支缺少测试覆盖
Why5 → 全球共享的认证基座未按"最大爆炸半径组件"实施
        分区域灰度与故障注入验证
        （系统性原因：全局单点 + 异常路径未按失效安全设计）
```

## 解决过程

工程师快速锁定 AK 服务（11 分钟），确认白名单数据异常后执行**白名单版本回滚**并分批重启 AK 服务应用，19:20 全球服务恢复。官方当晚发布事件说明致歉。行业普遍推断的整改方向：认证服务异常路径改造为 fail-static、白名单类元数据变更的校验与灰度、认证服务分区域单元化以切割全球爆炸半径。

## 经验教训

1. **认证服务是云平台的"全球心脏"**：区域隔离、多可用区在"全球共享的 IAM/AK 基座"面前全部失效——认证系统必须单元化/分区域部署，把爆炸半径切碎。
2. **异常处理路径就是可靠性的最后防线**：读取失败不可怕，可怕的是异常分支把损坏数据当正常结果发布——鉴权元数据必须 fail-static：校验不通过就用最后已知良好版本。
3. **管控面与数据面的解耦价值再次验证**：已运行业务无损让事故止于"管不了"而非"全死了"——这是云架构最重要的韧性分界线。
4. **半成品数据比无数据更危险**：完整性校验（记录数、checksum、版本签名）应是所有配置/元数据加载的强制前置。
5. 一年两次大故障的叠加效应说明：**信任修复的窗口比故障恢复的窗口长得多**，深度复盘的公开透明是止损的一部分。

## 预防与改进措施

- **预防（Prevent）**：白名单等鉴权元数据加载前完整性校验；异常分支单测与故障注入覆盖
- **减小爆炸半径（Contain）**：认证服务分区域单元化部署；管控面降级鉴权通道
- **快速检测（Detect）**：鉴权拒绝率突变告警（全局与分 Region）；元数据版本异常监控
- **快速恢复（Recover）**：元数据版本化与一键回滚（本案已达成，101min 恢复）；恢复剧本常态演练
