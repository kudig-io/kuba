# AWS S3 us-east-1 大规模中断（2017-02-28）：一条运维命令引发的连锁反应

## 摘要

2017 年 2 月 28 日，AWS 工程师在排查 S3 计费子系统缓慢问题时，按 Runbook 执行了一条移除少量服务器的命令，但命令参数输入有误，导致 us-east-1 区域内远超预期数量的服务器被移除——其中包括 S3 索引子系统（index）和放置子系统（placement）的服务器。两个子系统需要完全重启，而它们已多年未经历完整重启、规模远超以往，重启耗时数小时。期间 us-east-1 的 S3 GET/PUT/LIST 请求大面积失败，大量依赖 S3 的 AWS 服务（EC2 新实例启动、EBS 快照、Lambda 等）与互联网上无数网站/应用受牵连，主要影响持续约 4 小时 17 分钟。

## 影响评估（CRE 视角）

- **影响面**：us-east-1（AWS 最大区域）S3 全量客户；互联网上大量依赖该区域 S3 的网站与 App（含 Quora、Trello、IFTTT 等，第三方报道）
- **功能维度**：S3 对象读/写/列举全部失败；依赖 S3 的 EC2 新实例启动、EBS 快照创建、Lambda 执行受损
- **影响时长**：约 09:37–13:54（PST），即 17:37–21:54 UTC，约 4h17m
- **错误预算**：对 99.99% SLO 而言，一次消耗约 5 年预算（区域级）
- **次生影响**：**AWS 服务健康仪表板（SHD）的状态图标存储在 S3 上**，导致故障期间状态页无法正确显示故障状态，只能通过 Twitter 通报——状态页依赖故障系统本身的经典反例
- **对外沟通评估**：一般（故障中状态页失效削弱沟通）；事后复盘公开且坦诚，评级良好
- **定级依据**：AWS 最大区域的核心存储服务全面中断且外溢至社会面，定 SEV-1

## 技术细节与根因分析（SRE 视角）

### 背景架构

S3 由多个子系统组成：索引子系统管理全部对象的元数据与位置信息（服务 GET/LIST），放置子系统管理新对象的存储分配（服务 PUT）。二者均为大规模分布式系统，设计上可容忍局部容量损失。

### 因素三分

- **触发因素（Trigger）**：Runbook 命令的参数输入错误，移除的服务器集合远大于意图。
- **根本原因（Root Cause）**：
  1. 运维工具**缺少安全限幅**——允许一次性快速移除超过安全阈值的容量，且对"移除会导致子系统跌破最小容量"没有校验；
  2. 子系统**多年未做完整重启**，重启路径未随规模增长被验证，恢复时间远超预期。
- **扩大因素（Aggravating Factors）**：状态页依赖 S3 本身，客户沟通受阻；索引子系统重启期间必须完成安全检查与元数据完整性校验，规模越大耗时越长。

- **减轻因素（Mitigating Factor）**：S3 数据持久性未受影响（11 个 9 设计生效，无数据丢失）；其他区域 S3 完全正常。

### 5 Whys

```
现象：us-east-1 S3 请求大面积失败超过 4 小时
Why1 → 索引/放置子系统容量跌破最小阈值，需要完全重启
Why2 → 一条运维命令一次性移除了远超意图的服务器
Why3 → 工具允许快速移除任意规模的容量，无限幅与最小容量校验
Why4 → 该 Runbook 长期使用被视为低风险，工具防护未随 S3 规模演进
Why5 → 恢复慢：完整重启路径多年未演练，重启时间与系统规模不匹配（系统性原因：
        高危运维工具缺少防护 + 恢复路径缺少常态化验证）
```

## 解决过程

工程师确认容量损失后即启动子系统完全重启。重启过程需执行完整性校验，而两个子系统自多年前起未再完整重启过，期间 S3 规模增长了数倍，校验耗时远超预期。索引子系统 20:26（UTC）恢复读路径、21:18 完全恢复；放置子系统依赖索引子系统，21:54 恢复写路径。期间 AWS 通过 Twitter 与文字版状态页通报（图标加载依赖 S3 已失效）。

## 经验教训

1. 当运维工具可以移除生产容量时，必须内置**限幅（每次最多移除 X）与最小容量校验（低于水位线拒绝执行）**，否则任何一次输入错误都可能演变为区域级故障。
2. 当系统规模持续增长时，必须**定期演练完整冷启动/重启路径**并度量恢复时间，否则灾难恢复时间将随规模不可控地膨胀。
3. 当构建状态页/应急沟通通道时，必须保证其**不依赖被监控的系统本身**。
4. 大型子系统应**分解为更小的分区（Cell）**，使重启与故障影响可以按分区推进（AWS 官方后续措施）。

## 预防与改进措施

- **预防（Prevent）**：修改容量移除工具，增加移除速率限幅与最小容量保护（官方，事发当时已完成）
- **减小爆炸半径（Contain）**：加速 S3 子系统分区化（Cell 化）改造，把故障与重启限制在更小单元（官方）
- **快速检测（Detect)**：审计其它运维工具是否存在类似缺陷（官方）
- **快速恢复（Recover）**：将 SHD 状态页改造为跨区域、不依赖 S3 的架构（官方）

## SRE / CRE / FDE / SA 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 不是"手滑"问题：工具允许一条命令击穿最小容量、恢复路径从未按当前规模验证，才是根因 |
| CRE | 状态页依赖故障系统导致沟通失效，客户在最需要信息时得不到信息 |
| FDE | 恢复时间的主导项是"多年未演练的重启+校验路径"，冷启动时长必须成为常态化度量指标 |
| SA（客情危机） | S3 中断 4 小时+状态页依赖 S3 本身导致沟通受阻，客户'无法得知何时恢复'的焦虑被放大；AWS 详细 PES 成为行业教科书，但企业客户开始自建独立观测 |
| SA（技术危机） | 客户应配置跨区域复制（CRR）与独立于供应商的监控告警；状态页独立性是硬要求——客户的应急沟通通道绝不能依赖故障系统本身 |
