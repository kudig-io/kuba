# AWS ELB 平安夜故障（2012-12-24）：一次误删状态数据毁掉的圣诞夜

## 摘要

2012 年 12 月 24 日下午（太平洋时间），AWS us-east-1 区域的 ELB（弹性负载均衡）服务发生长时间故障：一名开发人员针对 ELB **生产环境**误运行了一个维护进程，**删除了大量生产负载均衡器的状态数据**。失去状态数据的 ELB 无法再正确管理后端配置——受影响的负载均衡器在客户随后进行任何配置变更（扩缩容、增删后端实例）时进入错误状态，流量转发异常。故障从 12:24 PST 开始，高峰期约 **6.8% 的运行中 ELB** 受影响；由于状态数据的恢复必须小心地与运行时状态合并、逐个负载均衡器修复，完整恢复耗时接近 **24 小时**（次日 12:05 PST）。恰逢平安夜流媒体高峰，**Netflix 大面积中断数小时**成为头条新闻。AWS 复盘承认：维护进程本不应能访问生产数据，**数据删除操作缺乏访问控制与审批闸门**；此后 ELB 状态数据访问改为显式变更审批制，并加速了快照式恢复能力建设。该案例与 GitLab 2017 误删并列为"人因+防护缺失"型故障的云端代表。

## 影响评估（CRE 视角）

- **影响面**：us-east-1 高峰约 6.8% 运行中 ELB 异常；Netflix 等大客户平安夜黄金时段流媒体中断数小时
- **影响时长**：约 23 小时（12-24 12:24 至 12-25 12:05 PST）
- **次生影响**：Netflix 事后公开反思并加速 Chaos Engineering 与多区域主动-主动架构（Isthmus/Active-Active 项目）
- **对外沟通评估**：良好——官方复盘坦承误操作与权限缺陷；但节日故障的舆论代价极高
- **定级依据**：区域级核心服务大面积长时间故障并击穿头部客户，SEV-1

## 技术细节与根因分析（SRE 视角）

### 背景架构

ELB 控制面维护每个负载均衡器的状态数据（后端实例列表、健康检查配置、DNS 关联等），数据面依据状态数据转发流量。状态数据完好时数据面可继续工作；一旦状态缺失，任何触发控制面动作的事件（客户变更、自动扩缩、健康事件）都会以损坏的状态重写负载均衡器配置。

### 因素三分

- **触发因素（Trigger）**：开发人员将本应针对维护环境的删除进程运行在了生产环境。
- **根本原因（Root Cause）**：生产状态数据的删除类操作**没有访问控制隔离与强制审批**，单人误操作即可直达生产数据。
- **扩大因素（Aggravating Factors）**：
  1. 删除未被立即发现，受影响 ELB 在随后数小时被"带毒变更"逐步破坏，损害面随时间扩大；
  2. 恢复需要状态数据与运行时的逐台一致性合并，无批量恢复工具，TTR 被拉长到近 24 小时；
  3. 平安夜流量高峰+值班薄弱时段，业务损失与响应速度双双恶化。

- **减轻因素（Mitigating Factor）**：ELB 核心转发功能在状态恢复后逐步正常；数据面在控制面恢复后自动重建。

### 5 Whys

```
现象：6.8% 的 ELB 异常近 24 小时，Netflix 平安夜中断
Why1 → ELB 状态数据被删除，后续控制面操作以损坏状态重写配置
Why2 → 维护用删除进程被误运行在生产环境
Why3 → 生产数据删除操作无环境隔离、无二次确认、无审批闸门
Why4 → 运维工具的权限模型按"信任操作者"设计而非"防呆"设计
Why5 → 缺乏针对"状态数据丢失"的快速恢复预案与演练
        （系统性原因：高危操作防护与恢复能力双缺失）
```

## 解决过程

团队在数小时排查后锁定状态数据缺失，立即冻结受影响 ELB 的自动变更以止损；随后从备份恢复状态数据，但必须与每个负载均衡器的当前运行时状态做一致性合并，只能逐个修复，历时至次日中午。事后整改：ELB 生产状态数据访问改为**显式的、需审批的变更流程**（CM 闸门）；建设状态数据快照与批量恢复能力；对高危维护工具做环境强隔离。

## 经验教训

1. **删除类操作必须防呆**：环境强隔离、干跑（dry-run）默认、二次确认、审批闸门——四道防线至少要有两道（GitLab 2017、语雀 2023 同款教训）。
2. **数据可以备份，恢复速度才是 SLA**：备份存在但无批量恢复工具，TTR 依然是 24 小时——恢复必须按"规模化恢复"演练。
3. **止损第一步是冻结变更**：状态损坏场景下，每一次自动/人工变更都在扩大损害面。
4. 客户侧（Netflix）的应对成为行业范式：**不信任单区域、用混沌工程持续验证容灾**——被故障教育出来的架构最可靠。
5. 节假日变更冻结（change freeze）与强化值班应成为制度。

## 预防与改进措施

- **预防（Prevent）**：生产数据删除操作的强制审批与环境隔离；维护工具默认指向非生产
- **减小爆炸半径（Contain）**：状态异常时自动冻结受影响资源的变更操作
- **快速检测（Detect）**：状态数据完整性周期校验与删除事件实时告警
- **快速恢复（Recover）**：状态快照+批量一致性恢复工具，按小时级 RTO 演练

## SRE / CRE / FDE 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | "备份存在≠可快速恢复"的规模化恢复课；高危工具防呆设计从此进入云厂商标配 |
| CRE | 头部客户在供应商故障中的最优解是自建韧性（Netflix 多区域+混沌工程），供应商 SLA 只是底线 |
| FDE | 损害面随时间扩大的"带毒变更"模式，要求取证同时冻结系统状态——止损与保全证据在此合流 |
