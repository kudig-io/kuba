# 携程 5·28（2015-05-28）：误删代码后，中国互联网第一次直播"全站重建"

## 摘要

2015 年 5 月 28 日上午 11 时左右，中国最大在线旅游平台携程的官网与 App **全面瘫痪**——首页无法打开、酒店/机票预订全部中断，页面一度直接报错。事故持续约 **12 小时**，至当晚 23:29 官网与 App 才恢复正常。携程官方最终定性：**员工错误操作，删除了生产服务器上的执行代码**导致服务不可用。故障期间"携程数据库被物理删除""程序员删库跑路"等谣言满天飞，携程股价盘前一度下跌，公众第一次围观了一家大型互联网公司**长达半天的全站恢复直播**。恢复过程之所以漫长，普遍分析指向：删除操作波及大量服务器上的应用发布内容，而携程当时的**发布/回滚系统无法快速将全量应用重新部署到数千台服务器**，只能大规模重装、验证、逐个业务拉起。该事件与同月支付宝光纤被挖断（5·27）接连发生，被业界并称"5·27/5·28"双大故障，直接推动了中国互联网行业对**生产环境操作权限管控、发布系统自动化与灾备演练**的大反思。

## 影响评估（CRE 视角）

- **影响面**：携程官网、App 全业务（酒店、机票、度假等预订与订单服务）全面不可用；旗下部分关联站点受牵连
- **影响时长**：约 12.5 小时（11:00 前后至 23:29 全面恢复）
- **次生影响**：谣言（删库跑路、数据被删）大规模传播；股价承压；OTA 订单流失（用户转向竞对）
- **对外沟通评估**：较差——官方口径更新缓慢、技术细节披露有限，谣言填补了信息真空；恢复后仅简短说明"员工错误操作删除执行代码"
- **定级依据**：全业务全渠道中断超 12 小时，SEV-1
- 未披露信息：误删操作的具体场景与工具、受影响服务器规模、内部问责结果

## 技术细节与根因分析（SRE 视角）

### 背景架构

携程为大型 OTA 平台，数千台生产服务器承载数百个应用。应用以发布系统分发的"执行代码"（编译产物/站点内容）形式运行于各服务器。生产环境运维操作当时依赖较高的人工权限，批量操作工具具备直接作用于大量服务器的能力。

### 因素三分

- **触发因素（Trigger）**：运维人员的错误操作删除了生产服务器上的应用执行代码（官方口径），影响范围覆盖核心业务集群。
- **根本原因（Root Cause）**：高危批量删除操作缺乏防护（权限过大、无二次确认/审批、无影响面预演）；同时**全量快速重建能力缺失**——发布系统无法在短时间内向数千台服务器重新部署全部应用，恢复只能靠半手工的漫长重装。
- **扩大因素（Aggravating Factors）**：
  1. 恢复路径从未按"全站重建"规模演练过，流程边摸索边执行；
  2. 应用间依赖复杂，拉起顺序与验证耗时巨大；
  3. 对外沟通迟缓，谣言放大品牌损伤。

- **减轻因素（Mitigating Factor）**：携程团队在 12.5 小时内恢复生产环境；无客户数据丢失（仅代码丢失）。

### 5 Whys

```
现象：全站瘫痪 12.5 小时
Why1 → 生产服务器上的应用执行代码被删除，服务无法运行
Why2 → 运维错误操作，批量删除作用于核心生产集群
Why3 → 高危操作无审批闸门、无影响面确认、权限范围过大
Why4 → 删除后无法快速恢复：发布系统不具备全量快速重部署能力
Why5 → "全站级恢复"从未被当作需求设计与演练——备份了数据，
        却没备份"把系统装回来的速度"
        （系统性原因：操作防护缺位 + 重建能力缺位的双重失守）
```

## 解决过程

携程内部全员应急：确认数据完整后，集中修复发布链路，向数千台服务器重新部署应用执行代码，按依赖顺序逐业务拉起与验证，23:29 全面恢复，官方致歉并公布初步结论。此后携程重构了发布系统（自动化、全量快速部署与回滚）、收紧生产操作权限并推行高危操作审批，业内普遍将此案作为运维安全管控的转折点案例。

## 经验教训

1. **删除类操作必须有系统性防呆**：权限最小化、二次确认、审批链、影响面预演——与 Atlassian 2022、Salesforce 2019 构成"误删三部曲"。
2. **恢复速度是被忽视的核心能力**：数据没丢仍瘫 12 小时——"从零重建全站需要多久"必须有答案且被演练（RTO 不只属于数据，也属于应用）。
3. **发布系统即灾备系统**：全量快速重部署能力在平时是效率，在灾难时是生命线。
4. **信息真空必被谣言填满**：重大故障的对外沟通要快、要有技术事实，否则"删库跑路"式叙事将主导舆论。
5. 连续故障（5·27 支付宝、5·28 携程）证明**行业性反思往往由标志性事故驱动**——不要浪费任何一次危机。

## 预防与改进措施

- **预防（Prevent）**：生产操作权限最小化与高危命令拦截；批量操作强制审批与影响面确认
- **减小爆炸半径（Contain）**：批量操作分批执行与速率限制；核心业务集群操作隔离
- **快速检测（Detect）**：应用存活与内容完整性监控，删除类异常即时告警
- **快速恢复（Recover）**：发布系统全量快速重部署能力；"全站重建"级恢复演练常态化

## SRE / CRE / FDE 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 数据备份完好仍瘫 12 小时——RTO 的瓶颈在"重建应用"而非"恢复数据"，恢复演练必须覆盖全站级场景 |
| CRE | 官方沉默让"删库跑路"成为公众记忆——事故叙事权的争夺从第一分钟开始 |
| FDE | 误删范围与操作路径的还原依赖操作审计日志——生产变更全量留痕是事后取证的底线 |
