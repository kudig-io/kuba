# 腾讯云 4·8（2024-04-08）：一次没做好灰度的升级，让所有客户登不上控制台

## 摘要

2024 年 4 月 8 日 15:23，腾讯云监控告警云 API 服务异常，随即工单、售后群与微博等渠道大量涌入"控制台登录不上"的客户反馈。故障持续**近 87 分钟**，共 **1957 个客户报障**。腾讯云事后发布公开复盘：故障源于云 API **新版本升级过程中的前向兼容性问题**——新版本接口协议与旧版本不兼容，而**灰度发布机制不足**使问题版本快速扩散到生产环境；由于控制台登录认证依赖云 API，客户无法登录控制台成为最直观的故障表现；同时云函数等**依赖云 API 提供产品能力的公有云服务**也连带不可用，形成管控面故障向产品面的级联扩散。回滚过程也暴露了问题：回滚所需的配置数据服务本身依赖云 API，出现"救火车堵在火场路上"的循环依赖，延长了恢复时间。腾讯云在复盘中承认灰度机制与兼容性验证不足，并公布了整改计划。该事件与阿里云 2023-11-12 AK 故障构成中国公有云"管控面单点"的姊妹案例：**云 API / 认证服务是云厂商的全局隐性单点，其变更必须按最高风险等级管理**。

## 影响评估（CRE 视角）

- **影响面**：全网客户控制台登录异常（云 API 认证不可用）；依赖云 API 的部分公有云服务（云函数、部分音视频与数据服务）无法使用；1957 个客户主动报障
- **影响时长**：15:23 告警至约 16:50 恢复，持续近 87 分钟
- **次生影响**：故障发生于工作日下午，大量企业运维操作中断；"腾讯云崩了"登上热搜，公有云可靠性再受舆论审视
- **对外沟通评估**：良好——一周内发布公开复盘（含时间线、根因、整改措施）并致歉，是中国云厂商中较完整的公开复盘之一
- **定级依据**：管控面全局不可用并级联影响部分产品面服务，SEV-1
- 未披露信息：受影响 API 调用总量、依赖服务的完整清单

## 技术细节与根因分析（SRE 视角）

### 背景架构

云 API 是腾讯云的统一管控入口：控制台登录认证、OpenAPI 调用、以及云函数等产品的内部能力调用均经由云 API 网关。云 API 自身按版本迭代升级，通过发布系统推送新版本至各集群。

### 因素三分

- **触发因素（Trigger）**：云 API 新版本发布，新版本接口协议存在前向兼容性问题，旧版本组件无法正确处理请求。
- **根本原因（Root Cause）**：变更管理失守——新版本兼容性验证不充分，且灰度发布机制不足，问题版本未在小流量阶段被拦截即扩散至全网。
- **扩大因素（Aggravating Factors）**：
  1. 控制台登录认证依赖云 API，管控面故障立即转化为全部客户可感知的登录失败；
  2. 云函数等产品面服务依赖云 API 提供能力，故障沿依赖链级联；
  3. 回滚所需的配置数据服务本身依赖云 API，形成循环依赖拖慢恢复。
- **减轻因素（Mitigating Factor）**：已运行的客户业务（数据面）大多不受影响；监控告警即时发现。

### 5 Whys

```
现象：控制台登录失败、依赖云 API 的服务中断 87 分钟
Why1 → 云 API 服务异常，认证与产品能力调用失败
Why2 → 新版本接口协议存在前向兼容性问题
Why3 → 兼容性验证与灰度机制不足，问题版本扩散至全网
Why4 → 管控面核心服务的变更未按最高风险等级设灰度闸门
Why5 → 回滚路径存在对故障服务自身的循环依赖，未做预案演练
        （系统性原因：管控面单点的变更防线与逃生路径缺失）
```

## 解决过程

告警后 8 分钟确认故障源为云 API 新版本，24 分钟内定位到前向兼容性问题并启动回滚；回滚过程中因配置数据服务受云 API 异常牵连而减速，工程师通过应急通道逐步恢复，16:50 全部服务恢复。复盘公布的整改：加强版本兼容性测试覆盖、重构灰度发布机制（小流量验证强制化）、消除回滚路径对云 API 的循环依赖、控制台登录增加独立逃生通道。

## 经验教训

1. **云 API / 认证是云厂商的全局单点**：与 Google 2020 认证故障、阿里云 2023 AK 故障同构——管控面核心服务的变更必须按"全网爆炸半径"管理，强制灰度与快速回滚。
2. **前向兼容性是升级的生死线**：新旧版本共存期的协议兼容必须双向验证（新读旧、旧读新），单向验证等于没验证。
3. **回滚路径不能依赖被回滚的系统**：逃生通道（配置获取、发布系统、应急登录）必须与主链路解耦并定期演练。
4. **管控面与数据面隔离救了大盘**：客户已运行业务基本无损，证明面向故障域的架构分层有效——但控制台是客户"眼睛"，看不见就是全崩。
5. **公开复盘是信任修复的最短路径**：一周内公布完整时间线与整改，成为中文云厂商透明度的正面样本。

## 预防与改进措施

- **预防（Prevent）**：接口协议双向兼容性测试；管控面变更最高风险等级审批
- **减小爆炸半径（Contain）**：强制小流量灰度与自动熔断；控制台登录独立逃生通道
- **快速检测（Detect）**：新版本发布期的接口错误率秒级监控与自动拦截
- **快速恢复（Recover）**：回滚路径去循环依赖；配置数据服务独立容灾预案演练
