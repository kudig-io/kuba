# AWS us-east-1 内部网络过载（2021-12-07）：自动扩容触发的连接风暴

## 摘要

2021 年 12 月 7 日，AWS us-east-1 区域一次内部服务的自动扩容动作触发了内部网络（AWS 服务自身运行所在的网络，与承载客户流量的主网络分离）中大量客户端的异常行为：连接激增叠加重试风暴，压垮了连接内部网络与主网络的网络设备。内部 DNS 与监控系统受损，AWS 自身的排障能力被削弱。EC2/STS 等控制面 API、管理控制台、以及依赖内部网络的服务（如 Fargate、EventBridge、部分 Route 53 API）持续受损约 7 小时。该事件是"控制面与数据面耦合""监控依赖故障网络"的教科书级案例。

## 影响评估（CRE 视角）

- **影响面**：us-east-1 全区域客户的控制面操作；大量美国用户日常服务（Disney+、Netflix、Ring、航空公司系统等，第三方报道）
- **功能维度**：EC2 启动新实例、STS 凭证签发、管理控制台登录、CloudWatch 指标延迟；已运行的 EC2 实例与 S3/DynamoDB 数据面基本不受影响
- **影响时长**：15:30–22:35 UTC 约 7h05m（官方时间线：7:30 AM–2:35 PM PST 后半段仍在恢复长尾）
- **错误预算**：区域控制面 99.9% SLO 的近全年预算一次耗尽
- **次生影响**：Support 联络中心依赖受损网络，客户在故障最初数小时**连工单都无法提交**；SHD 状态页更新系统同样受阻，早期沟通迟缓
- **对外沟通评估**：不足→良好（初期状态页更新明显滞后，官方复盘承认并承诺改造；事后发布了详细 RCA）
- **定级依据**：最大区域控制面级中断 7 小时、社会面影响广泛，定 SEV-1

## 技术细节与根因分析（SRE 视角）

### 背景架构

AWS 内部存在两张网络：**主网络**承载客户工作负载与部分 AWS 服务；**内部网络**承载 AWS 基础服务（监控、内部 DNS、授权等）。两网之间通过专用网络设备互联，该互联层的容量按历史流量模型配置。

### 因素三分

- **触发因素（Trigger）**：一次常规的内部服务自动扩容，导致大量客户端同时发起连接。
- **根本原因（Root Cause）**：内部网络客户端存在**缺陷的重试/退避行为**——连接失败后激进重试，形成正反馈的连接风暴；两网互联设备容量与保护机制不足以吸收该风暴。
- **扩大因素（Aggravating Factors）**：
  1. 内部监控系统依赖内部网络，故障后 AWS 自身可观测性受损，定位耗时大增；
  2. 内部 DNS 承载于同一拥塞路径，DNS 失败进一步放大所有服务的错误与重试；
  3. Support 系统与状态页更新流程依赖受损组件，对外沟通严重滞后。

- **减轻因素（Mitigating Factor）**：内部网络（internal network）与主网络分离的设计使控制面故障未波及数据面。

### 5 Whys

```
现象：us-east-1 控制面 API 高错误率约 7 小时
Why1 → 内部网络与主网络间的互联网络设备持续拥塞
Why2 → 内部网络客户端连接激增且失败后激进重试，流量正反馈放大
Why3 → 客户端库的退避机制在极端场景下失效（缺乏 jitter/熔断类保护）
Why4 → 互联层容量与保护（限流/优先级）未按"全体客户端同时重连"的最坏场景设计
Why5 → 监控与 DNS 等关键依赖与被保护网络同路径，故障时诊断与恢复手段同时失效
        （系统性原因：内部基础设施缺乏与故障域隔离的逃生通道）
```

## 解决过程

由于监控受损，团队初期只能依靠日志人工定位，显著拉长诊断时间。确认拥塞点后依次执行：将内部 DNS 流量迁出拥塞路径（17:15 恢复 DNS）→ 限流内部客户端连接活动 → 暂停触发流量的扩容活动 → 扩充互联设备容量。网络在 22:35 恢复。官方复盘明确表示：修复期间刻意放慢变更节奏，避免在已受损系统上引入新变量。

## 经验教训

1. 当客户端存在自动重连行为时，退避必须带**抖动（jitter）与上限**，并在服务端配套**准入限流**，否则任何瞬时扰动都可能被重试风暴放大为持续拥塞。
2. 当监控/DNS/工单系统与被监控网络共享故障域时，故障将同时摧毁"发现问题"和"处理问题"的能力——**观测与应急通道必须有独立故障域（out-of-band）**。
3. 网络互联层容量必须按**最坏情况（全量客户端同时重连）**做压测，而非历史均值。
4. 状态页更新必须有不依赖生产网络的发布通道（AWS 官方随后改造 SHD 并推出更细粒度的 Health Dashboard）。

## 预防与改进措施

- **预防（Prevent）**：修复内部客户端退避缺陷；对连接风暴场景增加网络设备侧保护（官方）
- **减小爆炸半径（Contain）**：加速内部服务迁出该互联路径、隔离故障域（官方）
- **快速检测（Detect）**：为内部网络建设独立于其自身的监控通道（官方）
- **快速恢复（Recover）**：改造 Support 系统与状态页，使其跨区域、不依赖单一网络（官方）

## SRE / CRE / FDE 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 重试风暴 + 容量按均值设计 = 自我维持的拥塞；退避与准入限流是分布式系统的生命线 |
| CRE | 客户最痛的不是故障本身，而是"控制台打不开、工单发不出、状态页没更新"三连 |
| FDE | 监控与故障共域导致"盲飞"，诊断时间成为 TTR 的主导项；独立观测通道价值在此刻兑现 |
