# ChatGPT 3·20（2023-03-20）：AI 原生应用的第一起大规模隐私串号事故

## 摘要

2023 年 3 月 20 日（太平洋时间），ChatGPT 用户陆续发现自己的**聊天历史侧栏里出现了别人的会话标题**——AI 时代第一起广受关注的大规模数据串号事故。OpenAI 确认问题后**主动将 ChatGPT 整体下线数小时**排查。官方复盘披露根因：**redis-py 客户端库的一个竞态条件缺陷**——OpenAI 使用 Redis 集群缓存用户会话信息，请求在入队后被取消（如用户中断）时，连接可能被**污染后放回连接池**：下一个复用该连接的请求会**读到上一个请求的响应数据**。3 月 20 日早晨的一次服务端变更意外推高了 Redis 请求取消率，使这个潜伏的竞态被大规模触发。除会话标题泄露外，更严重的影响是：**约 1.2% 的 ChatGPT Plus 订阅用户**在特定 9 小时窗口内的**支付相关信息**（姓名、邮箱、支付地址、信用卡后四位与有效期——不含完整卡号）可能对其他用户可见。OpenAI 修复库缺陷、通知受影响用户并与 Redis 维护者合作上游修复。该事件确立了 AI 原生服务的教训范式：**推理服务的会话缓存层是隐私事故的高危区**，取消/超时路径的连接状态管理必须严格审计。

## 影响评估（CRE 视角）

- **影响面**：全球 ChatGPT 用户的会话标题存在交叉可见风险；约 1.2% 的 Plus 订阅用户支付相关信息可能泄露（9 小时窗口内活跃者）；新建会话首条消息在极端情况下也可能被他人看到
- **影响时长**：主动下线与功能恢复合计约 9 小时（聊天历史功能恢复更晚，至次日）
- **次生影响**：意大利数据保护机构随后以隐私为由暂时封禁 ChatGPT（引用本事件）；全球监管对 AI 服务数据处理的审视升级
- **对外沟通评估**：优秀——技术复盘详细（含竞态机制与触发条件）、量化受影响比例、逐一通知受影响用户
- **定级依据**：非全量长时中断，但涉及支付信息级别的隐私泄露与监管后果，SEV-2
- 未披露信息：泄露信息被实际查看的次数、触发变更的具体内容

## 技术细节与根因分析（SRE 视角）

### 背景架构

ChatGPT 使用 Redis 集群缓存用户会话信息以降低数据库负载，Python 服务经 redis-py 客户端与 Redis 通信，使用共享连接池；请求-响应在异步模式下通过队列配对。用户中断、超时等场景会取消已入队的请求。

### 因素三分

- **触发因素（Trigger）**：一次服务端变更使 Redis 请求取消率异常升高，竞态触发频率从"忽略不计"跃升为"大规模发生"。
- **根本原因（Root Cause）**：redis-py 在"请求已发出但被取消"场景下的缺陷——连接带着未读取的响应数据被归还连接池，下一个复用者读到错位响应；应用层将他人数据当作自己的缓存命中返回。
- **扩大因素（Aggravating Factors）**：
  1. 缓存的是**用户身份强关联数据**（会话标题、账户信息），错位即隐私泄露；
  2. 低概率竞态在高流量基数下必然规模化兑现；
  3. 检测依赖用户报告——数据串号没有内建的完整性校验（如缓存值绑定用户 ID 验证）。

- **减轻因素（Mitigating Factor）**：无支付数据（PCI）泄露证据；OpenAI 主动下线服务而非被动等待，控制损害范围。

### 5 Whys

```
现象：用户看到他人会话标题，1.2% Plus 用户支付信息暴露风险
Why1 → Redis 缓存返回了错位的响应（他人数据）
Why2 → 被取消的请求把带残留响应的连接放回了连接池
Why3 → redis-py 取消路径的连接状态清理存在竞态缺陷
Why4 → 第三方客户端库的异常/取消路径未被自有测试覆盖，
        缓存读取无"数据属主校验"兜底
Why5 → 会话缓存被视为性能组件而非隐私边界组件，
        未按数据泄露风险设计防线
        （系统性原因：缓存层缺少属主校验的纵深防御）
```

## 解决过程

OpenAI 确认串号后主动下线 ChatGPT，定位 redis-py 竞态并部署修复；恢复服务但保持聊天历史关闭至彻底排查完成；向 redis-py 上游提交修复补丁；识别并逐一通知支付信息可能暴露的用户；发布详细复盘。整改包括：为缓存读取增加数据属主一致性校验、增强取消/异常路径测试、降低单点缓存故障的隐私影响面。

## 经验教训

1. **缓存层是隐私边界**：凡缓存用户身份关联数据，读取端必须校验"这条数据属于当前用户"——属主校验是缓存串号的最后防线。
2. **取消/超时路径是连接池类库的经典雷区**：异步取消后连接状态清理的正确性，必须纳入对第三方库的验收测试。
3. **低概率 × 高流量 = 必然事件**：竞态概率再低，在亿级请求下都会规模化兑现；触发率的突变（本案的取消率升高）就是引爆器。
4. **主动下线是隐私事故的正确决策**：与 Salesforce 2019 同款 fail-secure 逻辑——泄露不可逆，停服可恢复。
5. AI 原生服务的**监管暴露面远大于传统 SaaS**：一次技术性串号直接引发国家级封禁（意大利），隐私事故的合规成本必须计入架构决策。

## 预防与改进措施

- **预防（Prevent）**：第三方客户端库取消/异常路径的验收测试；连接池状态机审计
- **减小爆炸半径（Contain）**：缓存数据按用户隔离（键空间/加密绑定）；敏感字段不入共享缓存
- **快速检测（Detect）**：缓存读取属主校验失败即告警；串号类用户反馈的快速聚类识别
- **快速恢复（Recover）**：主动下线预案与分功能恢复（先核心对话、后历史记录）
