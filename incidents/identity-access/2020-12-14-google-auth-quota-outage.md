# Google 认证故障（2020-12-14）：配额归零 47 分钟，半个互联网"登不上了"

## 摘要

2020 年 12 月 14 日，Google 的**中央身份认证体系**全球中断约 47 分钟（约太平洋时间 03:47-04:32）：所有需要登录的 Google 服务——Gmail、YouTube、Google Drive、Docs、Meet、Calendar、Cloud Console 乃至第三方"Sign in with Google"（OAuth）——集体不可用；而无需登录的路径（如未登录状态的 Google 搜索、无痕模式看 YouTube）依然正常。官方复盘（事件编号 zall/20013）披露根因链条：Google 的 **User ID 服务**（认证体系的核心，负责用户账户唯一标识与认证凭据查询）依赖分布式存储，存储资源受**自动化配额管理系统**管控。数月前该配额系统进行迁移，User ID 服务的配额用量上报**未被正确纳入新系统**；宽限期（grace period）掩盖了问题，直至 12 月 14 日宽限期结束——自动化系统认为该服务"用量为零"，将其**存储配额自动降为 0**。User ID 服务无法写入且随后**读取过期数据被拒**，认证请求全面失败。这是"**自动化系统忠实执行错误数据**"的教科书案例：没有任何组件"坏了"，配额系统、存储系统、认证系统各自都在正确工作，唯独迁移期间丢失的一条用量数据让自动化做出了灾难性决策。恢复靠工程师禁用配额强制执行（fail open），服务在配额恢复后迅速回升。

## 影响评估（CRE 视角）

- **影响面**：全球所有依赖 Google 账户认证的服务：Gmail、YouTube（登录态）、Drive、Docs、Meet、Calendar、Google Cloud Console、Google Home、以及海量使用 Google OAuth 的第三方应用
- **影响时长**：约 47 分钟（03:47-04:32 PT）；恰逢欧洲工作时间上午、疫情期间远程办公/网课高峰，实际感知影响远超时长
- **次生影响**：Meet 网课/会议中断引发全球性讨论；智能家居设备（Google Home 控制的灯/温控）短暂失控成为"云依赖过深"的标志性新闻；第三方 OAuth 依赖方连带不可用
- **对外沟通评估**：良好——Google Cloud 发布了含根因、时间线与整改项的正式事件报告（zall/20013），Workspace 状态页同步更新；但故障期间状态页本身一度更新滞后
- **定级依据**：全球全量认证不可用、影响横跨消费者/企业/云三大产品线，SEV-1
- 未披露信息：受影响请求总量、第三方 OAuth 依赖方的具体数量

## 技术细节与根因分析（SRE 视角）

### 背景架构

Google 认证体系依赖 User ID 服务维护每个账户的唯一标识与认证凭据元数据，所有 OAuth 令牌签发与登录校验都要查询该服务。其底层分布式存储的资源用量由自动化配额管理系统统一管控——该系统按各服务上报的用量数据自动调整配额，防止资源滥用。为安全起见，User ID 服务对"数据新鲜度"有强约束：存储不可写时间过长后，读取路径会拒绝返回可能过期的凭据数据（安全优先设计）。

### 因素三分

- **触发因素（Trigger）**：迁移遗留问题的宽限期结束，自动化配额系统依据"用量为零"的错误上报数据，将 User ID 服务存储配额自动降为 0。
- **根本原因（Root Cause）**：配额系统迁移期间，User ID 服务的用量上报未被正确纳管——一条错误的元数据（用量=0）经过数月潜伏后被自动化忠实执行；且配额强制执行对"认证"这类全局单点服务没有 fail-static（维持现状）保护。
- **扩大因素（Aggravating Factors）**：
  1. 认证是 Google 全产品的**全局单点依赖**，一处配额归零即全线沦陷；
  2. 安全优先的"过期数据拒读"设计在此场景下把"不能写"升级为"不能读"，扩大了故障面；
  3. 宽限期机制让错误配置潜伏数月，迁移验证窗口早已关闭；
  4. 故障同时打击了部分内部工具与对外沟通渠道，减慢了响应与通告。
- **减轻因素（Mitigating Factor）**：无需登录的服务路径不受影响；自动化告警瞬时触发使定位相对迅速。

### 5 Whys

```
现象：全球所有 Google 登录/OAuth 认证失败 47 分钟
Why1 → User ID 服务存储配额被降为 0，写入失败且过期读取被拒
Why2 → 自动化配额系统依据"用量为零"的错误数据执行了缩减
Why3 → 配额系统迁移时该服务的用量上报未被正确纳入新系统
Why4 → 宽限期掩盖了迁移遗漏，迁移验证未覆盖"宽限期到期"场景
Why5 → 对认证级全局单点服务，配额自动化缺少 fail-static 保护
        与"归零级变更"的人工复核闸门
        （系统性原因：自动化对关键服务缺乏危险动作防护栏）
```

## 解决过程

告警爆发后，工程师快速将异常聚焦到 User ID 服务的存储配额，决策绕过正常配额流程、直接禁用配额强制执行（fail open），04:22 生效后服务迅速恢复，04:32 认证全面回升。官方整改项包括：审查并修复配额管理自动化对关键服务的行为——对"大幅缩减/归零"类变更增加保护栏与人工复核；为认证等全局服务的配额执行引入 fail-static 策略（异常时维持现状而非执行缩减）；改进迁移流程的验证覆盖（含宽限期到期路径）；增强故障期间的对外沟通韧性（状态页与通告渠道去除对被影响系统的依赖）。

## 经验教训

1. **自动化会忠实放大错误数据**：自动化系统本身没有故障——它只是把一条错误的元数据执行到底。凡自动执行"缩减/删除/归零"类危险动作，必须有独立数据源交叉验证或人工闸门。
2. **关键单点服务需要 fail-static**：对认证这类全局依赖，配额/策略执行系统在数据异常时应"维持现状"而非执行变更——宁可配额超用，不可认证归零。
3. **宽限期是双刃剑**：它给了迁移容错空间，也让错误潜伏到所有人遗忘之后爆发——迁移验收必须显式覆盖"宽限期到期"的行为。
4. **安全设计与可用性设计会互相冲突**：拒读过期凭据是正确的安全决策，但它把存储写入故障升级为全局认证中断——此类"安全优先"路径需要预演其可用性代价。
5. **认证就是最大的爆炸半径**：登录不可用时，用户无法区分"Gmail 坏了"还是"一切都坏了"——身份体系的容灾投入应按"全产品之和"而非单一服务评估。

## 预防与改进措施

- **预防（Prevent）**：配额自动化对关键服务的归零/大幅缩减动作加人工复核；迁移验收覆盖宽限期到期路径
- **减小爆炸半径（Contain）**：认证等全局单点的配额执行采用 fail-static；无登录路径保持独立可用
- **快速检测（Detect）**：配额即将大幅变更的预告警（执行前而非执行后）；用量上报断流检测
- **快速恢复（Recover）**：配额强制执行的一键旁路（break-glass）预案；状态页与通告渠道独立于被保护系统

## SRE / CRE / FDE 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 自动化危险动作（归零/缩减/删除）必须有防护栏：交叉验证、预告警、fail-static、break-glass 四件套缺一不可 |
| CRE | 47 分钟的中断因覆盖"全部需登录产品"而被感知为"Google 全挂了"——身份服务的 SLA 应按全产品聚合影响定义 |
| FDE | 根因潜伏数月、爆发于宽限期到期——取证需回溯到迁移时点的配置与上报数据，长周期变更审计日志是关键证据 |
