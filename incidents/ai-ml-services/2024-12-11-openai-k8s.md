# OpenAI 全平台中断（2024-12-11）：一个遥测服务打垮所有 K8s 控制面

## 摘要

2024 年 12 月 11 日 19:00 UTC 前后，OpenAI 部署了一个新的遥测（telemetry）服务到**所有集群**，用于采集 Kubernetes 控制面指标。该服务的配置意外导致每个节点都对 Kubernetes API Server 执行开销高昂的操作，数千节点同时发起，瞬间压垮了各集群的 K8s 控制面。**关键机制**：OpenAI 的服务发现依赖 K8s DNS（其后端是控制面），DNS 缓存使数据面在最初约 20 分钟内"看起来正常"，掩盖了问题并让部署继续推进到全部集群；缓存陆续过期后，服务发现全面失败，ChatGPT、API、Sora 全线中断。更棘手的是：**修复需要访问 K8s 控制面，而控制面已过载到无法访问**（运维人员被"锁在门外"）。团队通过缩小集群规模、封锁 API 管理访问、扩容 API Server 等手段夺回控制面访问权后删除问题服务，19:38 UTC 起集群陆续恢复，完全恢复约在 23:15 UTC。

## 影响评估（CRE 视角）

- **影响面**：全球全量用户与 API 客户（ChatGPT、API、Sora）
- **功能维度**：所有产品核心功能不可用或严重降级约 4.25 小时
- **影响时长**：约 19:00–23:15 UTC（不同产品恢复时间不同：API 21:36 基本恢复、ChatGPT 23:01 前后、Sora 23:15）
- **错误预算**：4 小时+ 全局中断，99.9% SLO 约半年预算
- **次生影响**：大量依赖 OpenAI API 构建的下游 AI 应用连带不可用——AI 原生应用生态首次大范围体会"模型供应商=关键基础设施"
- **对外沟通评估**：优秀——状态页持续更新，事后数日发布结构清晰的官方 RCA（含"我们如何被锁在控制面外"的坦诚描述）
- **定级依据**：全产品线全球中断超 4 小时，定 SEV-1

## 技术细节与根因分析（SRE 视角）

### 背景架构

OpenAI 运行数百个 K8s 集群，数据面（模型推理工作负载）依赖 **K8s DNS 做服务发现**，而 K8s DNS 记录最终由控制面（API Server/etcd）供给。控制面同时是运维操作（kubectl、删除工作负载）的唯一入口。遥测服务以 DaemonSet 类方式部署至**每个节点**。

### 因素三分

- **触发因素（Trigger）**：新遥测服务的 API 请求配置在大集群规模下产生海量高开销控制面调用。
- **根本原因（Root Cause）**：
  1. 变更**同时铺开到全部集群**，无按集群的分阶段发布——测试环境未暴露问题（开销与集群规模成正比，小集群测不出来）；
  2. **数据面对控制面存在隐性强依赖**（DNS 服务发现），控制面故障直接击穿数据面。
- **扩大因素（Aggravating Factors）**：
  1. **DNS 缓存双重恶化局面**：延迟了故障显现（让部署铺完全量）、又拉长了恢复确认周期；
  2. **运维锁定（lockout）**：修复动作依赖的控制面正是故障组件，无 break-glass 通道；
  3. 各集群需逐一夺回控制面，恢复呈长尾。

- **减轻因素（Mitigating Factor）**：API 关键路径在 4 小时内恢复；DNS 缓存机制使部分已缓存的客户不受影响。

### 5 Whys

```
现象：全产品线全球中断 4 小时+
Why1 → K8s DNS 服务发现失败，数据面无法互相寻址
Why2 → 各集群控制面（API Server）被打垮，DNS 记录无法刷新
Why3 → 新遥测服务在每个节点发起高开销 K8s API 调用，负载与集群规模成正比
Why4 → 变更未按集群灰度——小规模测试无法暴露规模相关缺陷，而全量铺开只用了几分钟
Why5 → 部署系统缺少"规模敏感型变更"的识别与强制分阶段机制；
        数据面-控制面解耦与控制面 break-glass 通道缺失（系统性原因）
```

## 解决过程

告警触发后团队较快锁定遥测服务，但删除它需要控制面访问权，而控制面已瘫痪——事件转化为"如何夺回控制面"：（1）缩小集群规模减少节点侧 API 负载；（2）在网络层封锁 K8s 管理 API 访问，切断遥测服务的请求来源，让 API Server 喘息；（3）直接扩容 K8s API Server 资源。三管齐下后陆续恢复各集群控制面访问，删除问题服务，再按集群分批恢复流量（部分流量被临时调度到健康集群）。官方 RCA 列出改进：分阶段部署强制化并增强监控、数据面与控制面解耦（服务发现不依赖实时控制面）、控制面 break-glass 应急访问机制、K8s 资源保护（API 优先级与公平性）、故障注入演练（含"控制面不可用"场景）。

## 经验教训

1. **开销与规模成正比的变更是最危险的一类**：小环境测试天然无效，必须按"集群规模梯度"灰度（小→中→大集群），并在每级间强制观察期。
2. **数据面绝不应强依赖控制面的实时可用性**：服务发现应能在控制面故障时以缓存/静态配置降级存活（官方明确此项改进）。
3. DNS/缓存会**同时延迟故障显现与恢复确认**——变更后的观察期必须长于相关缓存 TTL，否则"看起来没问题"毫无意义。
4. 必须预建**控制面 break-glass 通道**（独立的紧急访问路径、API 优先级与公平性保护），否则"修复工具与故障共死"会把小事故拖成大事故。
5. K8s API Server 需启用 **APF（API Priority and Fairness）等准入保护**，保证运维流量在过载时仍有最高优先级。
6. AI 原生应用的下游要认识到：**模型 API 是关键基础设施依赖**，需要多供应商/降级预案。

## 预防与改进措施

- **预防（Prevent）**：识别"规模敏感型变更"，强制按集群梯度分阶段发布（官方）
- **减小爆炸半径（Contain）**：数据面与 K8s 控制面解耦，服务发现可降级（官方）
- **快速检测（Detect）**：控制面健康与变更关联监控；观察期覆盖缓存 TTL（官方）
- **快速恢复（Recover）**：break-glass 控制面访问机制；APF 资源保护；控制面故障注入演练（官方）
