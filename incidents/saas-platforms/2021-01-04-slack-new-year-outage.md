# Slack 全球宕机（2021-01-04）：新年第一个工作日，办公软件最不能倒下的一天

## 摘要

2021 年 1 月 4 日——多数企业假期后的第一个工作日——Slack 发生全球性宕机约 **4 小时**（美东时间上午高峰段），全球用户无法发消息、无法加载频道。直接诱因是假期后**流量迅速回升**，但底层网络的 **AWS Transit Gateway（TGW）未能及时扩容**：Slack 的 AWS 多 VPC 架构依赖 TGW 互联，假期期间流量低谷使 TGW 缩至低容量档位，工作日流量陡增时 TGW 扩容速度跟不上，跨 VPC 网络出现**大规模丢包**。丢包引发连锁反应：Slack 的监控与指标系统自身依赖这张网络，工程师在最需要数据的时候**监控大面积失明**；同时 Web 层因下游超时触发激进扩容，新实例启动风暴又加剧了对配额与网络的压力，部分扩容甚至因触及 AWS 配额限制而失败。AWS 侧最终手动为 TGW 扩容，Slack 侧逐步恢复。官方复盘坦率披露了"云上租户无法直接控制底层网络扩容"的依赖困境，是 SaaS 依赖云网络容量管理的经典案例。

## 影响评估（CRE 视角）

- **影响面**：全球所有 Slack 用户；消息收发、频道加载、登录全面异常
- **影响时长**：约 4 小时（美东上午 ~10:00 前后至 14:00 前后分批恢复）
- **次生影响**：发生在假期返工首日，企业协作停摆的感知被最大化放大；"Slack is down" 全球热搜
- **对外沟通评估**：优秀——工程博客深度复盘，坦承监控失明与云依赖问题
- **定级依据**：核心产品全球性不可用数小时，SEV-1
- 未披露信息：受影响消息量、具体丢包率峰值

## 技术细节与根因分析（SRE 视角）

### 背景架构

Slack 运行在 AWS 多 VPC 架构上，各 VPC（Web、后端、数据、监控）通过 AWS Transit Gateway 互联。TGW 由 AWS 管理并按流量自动伸缩——租户不可见、不可干预。Slack 的监控栈与被监控系统共享这张跨 VPC 网络。

### 因素三分

- **触发因素（Trigger）**：新年首个工作日流量从假期低谷陡增，TGW 自动扩容速度跟不上流量攀升斜率。
- **根本原因（Root Cause）**：关键网络基础设施（TGW）的容量伸缩由云厂商黑盒管理，无法针对可预期的流量事件（假期返工）预热扩容；Slack 侧也未向 AWS 预约容量。
- **扩大因素（Aggravating Factors）**：
  1. 监控系统与生产共享同一故障网络，故障期间**可观测性同步失效**，定位严重减速；
  2. Web 层激进自动扩容在网络异常下形成实例启动风暴，触及 AWS 配额上限，制造第二重混乱；
  3. 丢包导致的超时重试放大了网络负载（重试风暴）。

- **减轻因素（Mitigating Factor）**：Slack 的数据面在容量恢复后逐步正常；无数据丢失。

### 5 Whys

```
现象：新年首个工作日 Slack 全球不可用约 4 小时
Why1 → 跨 VPC 网络大规模丢包，服务间调用大面积超时
Why2 → AWS Transit Gateway 容量不足，扩容速度跟不上流量回升
Why3 → 假期低谷使 TGW 缩容，可预期的返工流量高峰未做容量预热
Why4 → TGW 是云厂商黑盒，租户无预热接口，Slack 也未与 AWS 预约
Why5 → 对"云托管网络也需要容量管理"缺乏认知，且监控与生产
        共享故障域，失明加剧了故障时长
        （系统性原因：云依赖容量盲区 + 可观测性自依赖）
```

## 解决过程

工程师在监控部分失明的情况下通过残存指标与 AWS 支持联合定位到 TGW 瓶颈；AWS 手动为 TGW 扩容；Slack 侧处理扩容风暴与配额问题，网络恢复后分批放量恢复服务。事后改进：与 AWS 建立可预期流量事件的容量预热机制、监控链路与生产网络故障域隔离、自动扩容加装抑制阀。

## 经验教训

1. **云托管的"自动伸缩"不等于"无限且及时"**：TGW、NAT 网关、负载均衡器都有伸缩速率极限，可预期的流量事件必须提前预热或预约容量。
2. **监控必须与生产隔离故障域**：与被监控系统共享网络/区域的监控，在最关键时刻必然失明——带外监控（out-of-band）是刚需。
3. **自动扩容需要抑制机制**：网络异常时的扩容风暴会撞配额、抢资源，把网络故障升级为计算故障。
4. **假期效应是容量管理的固定考点**：流量低谷导致的缩容，会在返工日成为陷阱（与 Slack 同日返工的还有全球企业 IT）。
5. 云租户要建立与云厂商的**联合应急通道**：黑盒组件故障时，厂商支持响应速度直接决定 TTR。

## 预防与改进措施

- **预防（Prevent）**：可预期流量事件（假期返工、大促）前与云厂商预约容量预热
- **减小爆炸半径（Contain）**：自动扩容速率上限与配额余量监控；重试预算防止重试风暴
- **快速检测（Detect）**：带外监控独立于生产网络；跨 VPC 丢包率专项告警
- **快速恢复（Recover）**：与云厂商的紧急升级通道（TAM/Support）演练；分批放量恢复预案
