# 复盘方法论总览

kuba-database 对每个故障案例采用三重视角进行复盘。三者互补，共同构成完整的故障分析框架：

| 视角 | 关注点 | 核心问题 | 在案例中的落点 |
|---|---|---|---|
| **SRE**（Site Reliability Engineering） | 系统与流程 | 系统为什么会失效？如何让它不再失效？ | 根因分析、时间线、预防措施 |
| **CRE**（Customer Reliability Engineering） | 客户与信任 | 客户感知到了什么？沟通是否及时透明？ | 影响评估、对外沟通、SLA/SLO 视角 |
| **FDE**（Field Data Engineering） | 数据与证据 | 现场数据（指标/日志/链路）如何还原真相？ | 时间线佐证、检测缺口、可观测性改进 |

## 三视角如何协同

1. **FDE 先行**：一切结论必须有数据支撑。时间线中的每个关键节点应能对应到指标突变、日志证据或外部观测（如第三方监控、社交媒体信号）。
2. **SRE 定因**：在数据基础上区分三类因素——
   - **触发因素（Trigger）**：直接引发故障的事件（一次变更、一条命令、一个请求）。
   - **根本原因（Root Cause）**：使触发因素得以造成破坏的系统性缺陷。
   - **扩大因素（Aggravating Factors）**：使影响范围扩大、恢复时间延长的因素（如监控依赖故障系统本身、回滚通道失效）。
3. **CRE 定损**：从客户侧度量影响——受影响用户比例、功能维度（读/写/登录/支付）、错误预算消耗、沟通时延（故障发生 → 首次对外通告）。

## 无指责原则（Blameless）

- 人会犯错是常量，**系统允许单个错误造成大范围破坏才是变量**。
- 复盘中禁止出现对个人的追责表述；所有"人为失误"必须转写为可改进的系统缺陷（缺少防护、缺少确认、缺少灰度）。
- 详见 [sre-postmortem.md](sre-postmortem.md)。

## 每个案例的方法论落地检查

- [ ] 时间线的关键节点有数据/来源佐证（FDE）
- [ ] 明确区分 Trigger / Root Cause / Aggravating Factors（SRE）
- [ ] 至少一条完整的 5 Whys 链或贡献因素图（SRE）
- [ ] 记录 TTD（检测耗时）、TTM（缓解耗时）、TTR（完全恢复耗时），无法获知时标注"未披露"（FDE）
- [ ] 评估客户影响面与官方沟通表现（CRE）
- [ ] 每条经验教训对应至少一条可执行的预防措施（SRE/CRE）
