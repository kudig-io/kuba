# 阿里云香港（2022-12-18）：冷机停转 14 小时，管控面暴露单 AZ 软肋

## 摘要

2022 年 12 月 18 日，阿里云香港 Region 可用区 C 机房因**制冷系统全面失效**发生大规模服务中断——阿里云官方称之为"**运营十多年来持续时间最长的一次大规模故障**"。08:56 温控告警后，机房 4 台主冷机因**冷却水路缺水进气形成气阻**集体异常，按预案切换 4 台备冷机时，**主备共用同一水路循环系统**，气阻导致切换失败；补水排气后又被冷机**群控逻辑死锁**卡住——无法单台独立启动，直至设备供应商现场手工解锁群控（15:20 首台恢复，18:55 四台恢复），制冷中断超过 10 小时。期间机房高温迫使全面降载、关机，一个包间更因温度达到临界值**触发消防喷淋**，电源柜与多列机柜进水、硬件损坏。可用区 C 的 ECS/EBS/RDS/OSS 大面积中断（单 AZ 冗余 OSS 从 11:07 中断至次日 00:30）。故障还外溢出可用区：**香港 Region 的 ECS 管控面（Control Plane）因客户涌向其他可用区购买实例而过载限流，可用性最低跌至 20%**，且扩容受阻——新管控节点依赖的中间件、自定义镜像服务竟分别单点部署在故障的可用区 C。事后复盘披露四大问题（冷机恢复慢、喷淋处置不当、管控单 AZ 依赖、信息发布迟缓），推动阿里云新版 Status Page 上线。这是"物理设施故障 × 管控面隐藏单点"复合灾难的中文云计算标志案例。

## 影响评估（CRE 视角）

- **影响面**：香港可用区 C 的 ECS、EBS、OSS（单 AZ 版）、RDS、NAT 等全线服务中断；香港 Region 级 ECS 管控 API 可用性最低跌至 20%；Dataworks、K8s 控制台受牵连；澳门部分政企网站（如澳觅、MFood 等本地服务）瘫痪
- **影响时长**：主体约 15.6 小时（08:56 告警至 22:50 最后包间恢复供电，按 934 分钟计）；单 AZ OSS 至次日 00:30；部分 RDS 单机实例恢复更久
- **次生影响**：消防喷淋造成硬件损坏与数据安全检查长尾；跨可用区未做多活的客户全程不可用；公有云"可用区隔离"承诺的边界（管控面共享）被公开检视
- **对外沟通评估**：官方承认"信息发布不够及时透明"、Status Page 更新滞后引发客户困惑；12-25 发布的复盘详尽坦诚（含分钟级时间线与四项整改），为国内云厂商罕见
- **定级依据**：区域级长时中断+管控面跨 AZ 外溢+硬件损毁，SEV-1
- 未披露信息：受影响客户数量、赔偿总额、冷机供应商细节

## 技术细节与根因分析（SRE 视角）

### 背景架构

香港可用区 C 为单一物理机房，制冷依赖 4 主 4 备共 8 台冷水机组——但主备**共用同一套冷却水路循环系统**，且冷机受群控系统统一管理。ECS 管控为 B/C 可用区双机房容灾；但管控扩容依赖的中间件服务、自定义镜像数据服务（依赖单 AZ 版 OSS）都单点部署在可用区 C。OSS 提供单 AZ（LRS）与 3AZ（ZRS）两种冗余，RDS 部分实例依赖部署在 C 区的代理服务。

### 因素三分

- **触发因素（Trigger）**：机房冷却系统缺水进气形成气阻，导致 4 台主冷机服务异常。
- **根本原因（Root Cause）**：制冷系统存在两个设计级单点——主备冷机**共用水路**（气阻同时废掉主备）与**群控逻辑死锁**（无法单台独立启动）；冗余设计只在纸面成立，未覆盖共因失效（common cause failure）。
- **扩大因素（Aggravating Factors）**：
  1. 现场处置不及时，包间温度达临界触发消防喷淋，硬件进水损坏拉长恢复；
  2. ECS 管控容灾在真实故障中失效：C 区故障 + 客户购买潮 + 实例拉起流量三重叠加压垮 B 区管控，扩容又被"中间件在 C 区"卡死；
  3. 自定义镜像服务依赖 C 区单 AZ OSS，客户在其他可用区新购实例也启动失败（故障跨 AZ 传导）；
  4. 部分 RDS 跨 AZ 实例因依赖 C 区代理服务而切换失败；
  5. Status Page 更新不及时，客户在信息真空中决策。
- **减轻因素（Mitigating Factor）**：多可用区部署的客户业务基本无损；OSS 3AZ（ZRS）服务基本未受影响；网络产品 12:45 前完成容灾逃逸。

### 5 Whys

```
现象：可用区 C 服务中断超 15 小时，管控面影响外溢全 Region
Why1 → 机房制冷失效超 10 小时，服务器高温停机/关机保护
Why2 → 主备 8 台冷机全部无法工作：水路气阻 + 群控无法单台启动
Why3 → 主备共用水路循环系统（共因失效）；群控逻辑存在死锁且
        无手工独立启动预案
Why4 → 基础设施冗余评审未覆盖"共因失效"与"群控系统自身故障"
Why5 → 管控面与数据面的依赖拓扑（中间件/镜像 OSS 单点在 C 区）
        从未按"单 AZ 全灭"场景演练
        （系统性原因：物理冗余纸面化 + 管控依赖拓扑失察）
```

## 解决过程

按预案主备切换失败后，阿里云启动应急通风降温、全面降载与分批关机保数据；冷机供应商到场补水排气、手工解锁群控后逐台恢复冷机（15:20-18:55）；随后分批启动服务器，对喷淋受损包间执行严格数据完整性检查后再供电（22:50）；管控 API 23:11 恢复，单 AZ OSS 次日 00:30 恢复。官方 12-25 发布复盘并公布四项整改：机房设施管控系统全面检查（监控覆盖度、切换逻辑防死锁）；温升预案标准化与常态演练（明确关机/断电动作）；全网巡检消除多 AZ 产品对单 AZ OSS/中间件的依赖、加强管控面容灾演练；上线新版 Status Page 提升信息发布速度。

## 经验教训

1. **冗余必须审查共因失效**：4+4 主备冷机共用一套水路 = 冗余为零；群控系统本身也是单点——物理设施的 FMEA 要像审代码一样审"共享依赖"。
2. **管控面是隐藏的 Region 级共享单点**：数据面按 AZ 隔离，管控面却全 Region 共享且其依赖（中间件、镜像 OSS）藏着单 AZ 单点——"单 AZ 全灭"必须成为管控面的标准演练场景。
3. **故障会诱发客户行为风暴**：客户涌向其他 AZ 购买实例的"逃生流量"压垮管控——容灾容量要按"故障日峰值"而非日常峰值规划。
4. **温升处置窗口极短**：从降载到喷淋只有 4 小时——数据中心温升预案的关机决策必须果断前置，犹豫的代价是硬件进水。
5. **单 AZ 产品要明码标价风险**：LRS OSS、单机 RDS 在 AZ 级灾难中无路可逃——云厂商与客户都需把"AZ 级全灭"纳入选型评估。
6. Status Page 在最需要时失灵是行业通病（AWS 2020 同款）——**状态发布链路必须独立于故障域**。

## 预防与改进措施

- **预防（Prevent）**：机房设施 FMEA 覆盖共因失效（共享水路/群控）；设施管控切换逻辑防死锁审查
- **减小爆炸半径（Contain）**：管控面依赖去单 AZ 化；温升预案标准化（前置关机决策）避免喷淋
- **快速检测（Detect）**：设施监控数据采集扩大覆盖与精细度，加速定位
- **快速恢复（Recover）**：冷机手工独立启动预案与演练；管控面"单 AZ 全灭"容灾逃逸演练；新版 Status Page 快速发布
