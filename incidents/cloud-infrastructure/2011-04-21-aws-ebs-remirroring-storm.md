# AWS EBS 风暴（2011-04-21）：云计算的第一次系统性信任危机

## 摘要

2011 年 4 月 21 日凌晨，AWS 在 us-east-1 区域执行一次常规网络扩容变更时，**误将一个可用区内 EBS 集群的流量切换到了容量很低的备用网络**上。EBS 节点间的复制链路瞬间中断，大量节点认为副本丢失，同时发起**重新镜像（re-mirroring）**寻找空间——这场"re-mirroring 风暴"迅速耗尽了该 EBS 集群的空闲容量，节点陷入"寻找空间-失败-重试"的循环（stuck volumes），并进一步把 EBS 控制面的线程池拖垮，使**控制面故障蔓延到整个区域的多个可用区**。高峰期该可用区约 **13% 的 EBS 卷**卡死，依赖 EBS 的 EC2 实例与 RDS 数据库大面积不可用，Reddit、Quora、Foursquare 等大批知名网站宕机。完全恢复历时约 **4 天**，且约 0.07% 的受影响卷数据无法恢复。AWS 发布了长篇官方复盘，承认变更执行错误、重试风暴设计缺陷与控制面隔离不足，并向受影响客户提供 10 天服务抵扣。该事件是云计算史上第一次全行业级信任危机，"Multi-AZ 不等于免疫控制面故障"从此写入所有云架构教科书。

## 影响评估（CRE 视角）

- **影响面**：us-east-1 一个可用区约 13% EBS 卷卡死；EBS 控制面劣化波及全区域；EC2/RDS 及其上大批互联网服务中断
- **影响时长**：主要影响约 4 天（4 月 21 日至 24 日逐步恢复）；约 0.07% 受影响卷数据永久丢失
- **错误预算**：以 99.95% 目标计，一次事件耗尽数年预算
- **次生影响**：Reddit/Quora/Foursquare 等长时间宕机引发公众对"云"的第一次广泛质疑；催生跨区域容灾与"设计面向失败"（Design for Failure）实践普及
- **对外沟通评估**：复盘优秀（数千字技术细节+赔偿），但故障期间状态页更新滞后遭批评
- **定级依据**：区域级多服务中断数日且有数据丢失，SEV-1

## 技术细节与根因分析（SRE 视角）

### 背景架构

EBS 由存储节点集群 + 控制面组成：每个卷两副本，节点间通过高带宽主网络复制；副本失联时节点主动 re-mirroring（找新空间复制数据），期间卷 I/O 挂起。控制面为区域级共享服务，服务所有 AZ。备用低容量网络仅为管理用途设计。

### 因素三分

- **触发因素（Trigger）**：网络变更操作失误，主网流量被切到低容量备用网络，复制链路大面积中断。
- **根本原因（Root Cause）**：re-mirroring 机制在大规模并发失联场景下无退避、无容量感知，形成自我强化的重试风暴（thundering herd）；控制面与单集群故障无隔离。
- **扩大因素（Aggravating Factors）**：
  1. 集群空闲容量按常态故障率预留，无法吸收全集群同时 re-mirror；
  2. 控制面线程池被慢请求占满，故障从数据面上升到区域级控制面；
  3. 客户普遍将 Multi-AZ 视为充分容灾，未做跨区域预案，实际控制面是区域级共享单点。

- **减轻因素（Mitigating Factor）**：EBS 数据的持久性未受影响（数据未丢失）；AWS 后续添加了显式的流量控制机制。

### 5 Whys

```
现象：一个 AZ 的 EBS 大面积卡死 4 天，控制面劣化波及全区域
Why1 → EBS 节点集体 re-mirroring 耗尽集群容量后陷入重试循环
Why2 → 复制网络被误切到低容量备用网，副本大面积"假失联"
Why3 → 变更执行流程允许把生产复制流量切到不满足容量的网络（无自动核算）
Why4 → re-mirroring 无全局退避/熔断设计，控制面对慢请求无隔离舱壁
Why5 → 系统按"少量随机故障"建模，未考虑相关性故障（全集群同时失联）
        （系统性原因：恢复机制自身成为放大器 + 控制面隔离缺失）
```

## 解决过程

AWS 先禁用故障集群的控制面 API 交互，阻止风暴继续拖垮区域控制面；随后向故障集群紧急增补物理存储容量，让卡死节点的 re-mirroring 得以完成，分批解冻卷；无法恢复的卷从快照重建，最终约 0.07% 受影响卷数据丢失。官方复盘承诺：re-mirroring 增加退避与容量感知、控制面按 AZ 分区隔离、变更流程增加网络容量校验，并向客户普及跨 AZ/跨区域架构指导。

## 经验教训

1. **恢复机制必须为"相关性故障"设计**：为随机单点故障设计的自愈（re-mirror）在批量故障下会变成放大器——退避、熔断、容量感知缺一不可。
2. **控制面是比数据面更危险的共享单点**：Multi-AZ 保护数据面，控制面故障仍是区域级——控制面必须分区隔离并做舱壁模式。
3. **变更工具应内建容量核算**：把流量切到某网络前自动校验其容量承载能力。
4. 客户侧教训成为行业共识：**"面向失败设计"**、跨区域容灾、避免对单区域控制面的强依赖。
5. 数据丢失（0.07%）证明：**快照/备份是最后防线**，复制不等于备份。

## 预防与改进措施

- **预防（Prevent）**：变更流程网络容量自动校验；re-mirroring 退避与全局速率限制
- **减小爆炸半径（Contain）**：EBS 控制面按 AZ 分区；慢请求舱壁隔离
- **快速检测（Detect）**:复制链路失联规模与 re-mirror 队列深度告警
- **快速恢复（Recover）**：紧急容量增补预案；从快照批量重建工具
