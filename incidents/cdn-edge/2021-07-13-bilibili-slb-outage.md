# B 站 713（2021-07-13）：一个 "0" 字符串引发的全站雪崩

## 摘要

2021 年 7 月 13 日 22:52 起，哔哩哔哩（B 站）全站不可用——App、Web、直播全线报错，"B 站崩了"瞬间登顶热搜，甚至带动"A 站崩了""豆瓣崩了"等连锁话题（用户涌入压垮友站）。官方一年后发布的深度复盘揭示了教科书级根因：B 站自研 SLB（基于 OpenResty/Lua）的**加权轮询负载均衡代码存在缺陷**——某个服务注册时上报的 weight 值为**字符串 "0"**，Lua 作为弱类型语言在算术运算中将其转为数字 0，代码进入了处理权重为 0 的特殊分支，而该分支存在缺陷，导致**求最大公约数的递归函数陷入死循环**，SLB 集群 CPU 瞬间打满 100%，无法处理任何请求。更痛的是恢复过程：工程师最初怀疑是变更引起，**三次回滚均无效**（22:55~23:55），因为触发条件（weight="0" 的注册数据）仍然存在；23:23 多活机房 SLB 恢复使部分业务（App 推荐、直播等）先行恢复；最终团队选择**新建一组 SLB 集群**并重新接入流量，主站于次日 01:00 前后恢复，全部长尾至 02:00+。713 复盘以罕见的坦诚披露了定位曲折、多活覆盖不全、平台工具循环依赖等问题，成为中文互联网最有影响力的事故复盘之一。

## 影响评估（CRE 视角）

- **影响面**：B 站全平台（App/Web/TV 端）核心功能不可用；直播、视频播放、评论互动中断；连带话题效应波及其他网站
- **影响时长**：核心不可用约 3 小时（22:52 至次日 01:00 主站恢复）；部分能力 23:23 起经多活先行恢复
- **次生影响**："B 站崩了"全网热搜第一；用户涌入友站造成连锁压力；次日股价受扰动
- **对外沟通评估**：事发当晚仅简短公告；一年后发布深度技术复盘，坦诚度获全行业好评（迟到但高质量）
- **定级依据**：全站级不可用数小时、社会关注度极高，SEV-1
- 未披露信息：具体收入损失、上报 weight="0" 的服务细节

## 技术细节与根因分析（SRE 视角）

### 背景架构

B 站入口流量经自研 SLB（OpenResty + Lua 实现的七层负载均衡）分发到各业务。SLB 的加权轮询算法用 Lua 实现，服务实例的 weight 来自服务注册中心的动态数据。部分核心业务建设了同城多活（另一机房独立 SLB），但覆盖不全；SLB 自身的发布与管理平台又依赖 SLB 转发（循环依赖）。

### 因素三分

- **触发因素（Trigger）**：某服务在发布过程中向注册中心上报了 weight 为字符串 "0" 的实例数据，SLB 动态加载后进入缺陷分支。
- **根本原因（Root Cause）**：Lua 加权轮询代码在 weight=0 场景下的处理分支存在缺陷——gcd（最大公约数）递归在该输入下永不终止；弱类型语言把字符串 "0" 悄悄转成数字 0，绕过了"字符串类型不合法"的直觉防线；输入数据无 schema 校验。
- **扩大因素（Aggravating Factors）**：
  1. 死循环发生在 SLB 数据面，CPU 100% 使 SSH/管理通道近乎失效，排查与操作极其困难；
  2. 三次回滚无效——回滚只能撤销"变更"，撤不掉"数据"，触发数据一直在注册中心；
  3. 多活覆盖不全：未覆盖的核心业务（主站页面等）无路可逃；
  4. SLB 管理平台依赖 SLB 自身（循环依赖），故障时工具也瘫痪；
  5. 新建集群成为唯一出路，但新建+接入流程未预演，耗时近 1 小时。

- **减轻因素（Mitigating Factor）**：SLB 集群的 cell 化架构使其他区域负载均衡器未受影响；手动恢复后服务逐步回稳。

### 5 Whys

```
现象：SLB 集群 CPU 100%，全站不可用约 3 小时
Why1 → SLB Lua 加权轮询代码陷入死循环，耗尽全部 CPU
Why2 → 某实例 weight 为字符串 "0"，被 Lua 隐式转为 0 进入缺陷分支
Why3 → weight=0 分支的 gcd 递归缺少终止条件；注册数据无类型校验
Why4 → 异常输入场景（weight=0/非法类型）无单测与混沌测试覆盖
Why5 → SLB 这类"全站单点"的代码质量、输入防御、逃生路径
        （多活/新建预案）均未按其爆炸半径配置投入
        （系统性原因：入口单点的防御纵深与恢复预案双不足）
```

## 解决过程

告警后工程师在管理通道近乎失效的条件下排查，先恢复多活机房 SLB 使部分业务逃生（23:23）；对主集群三次回滚无效后，果断放弃"修复现有集群"，转为**新建 SLB 集群重新接入流量**，主站约 01:00 恢复。事后整改（复盘披露）：修复 Lua 权重算法缺陷并补齐输入校验；推进同城多活全覆盖与"多活即逃生"标准化；解除管理平台对 SLB 的循环依赖；建设 SLB 快速重建与流量切换预案；完善高负载下的带外管理通道。

## 经验教训

1. **弱类型语言在基础设施层是放大器**：字符串 "0" 与数字 0 的隐式转换绕过了所有直觉——基础组件的外部输入必须做强 schema 校验。
2. **回滚不是万能钥匙**：数据触发型故障回滚变更无效——应急决策要尽早区分"变更引发"与"数据引发"，避免在无效路径上消耗黄金时间。
3. **多活的价值=覆盖率**：23:23 多活业务先行恢复证明了多活有效，但未覆盖的业务瘫满全程——多活必须全覆盖并常态演练切换。
4. **管理面不能依赖数据面**（循环依赖）：救火工具必须在火灾中可用，带外通道是入口组件的标配。
5. **重建优于修复**：对入口级单点，"快速新建一套"应是预案而非急中生智——B 站当晚靠它救场，但耗时本可更短。

## 预防与改进措施

- **预防（Prevent）**：SLB 输入数据强校验（类型/取值域）；权重算法边界值单测与模糊测试
- **减小爆炸半径（Contain）**：同城多活全覆盖，入口流量可秒级切换；SLB 集群分组隔离
- **快速检测（Detect）**：SLB CPU/延迟不变量告警（已达成 3min）；注册中心异常数据审计
- **快速恢复（Recover）**：SLB 快速重建与接入预案工具化演练；管理平台带外部署解除循环依赖
