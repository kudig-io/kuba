# Datadog 全球宕机（2023-03-08）：一次没人按下按钮的"部署"

## 摘要

2023 年 3 月 8 日 06:03 UTC 起，可观测性巨头 Datadog 发生成立以来最严重的故障：横跨 **AWS、GCP、Azure 三朵云的 5 个区域**、全线产品（指标、日志、APM、告警）同时受损，完全恢复历时约 **27 小时**（至 3 月 9 日 08:58 UTC）。触发者不是任何人的变更，而是**操作系统的自动安全更新**：一批 Ubuntu 主机上启用的 systemd 无人值守升级（legacy security update channel）在各云区域**几乎同时**自动应用了一个 systemd 更新，systemd 重启时与网络栈（systemd-networkd 与 Cilium/eBPF 路由规则）的交互**清空了节点的网络路由规则**，数万个节点瞬间网络失联。Kubernetes 集群随之大乱：失联节点被标记异常，控制面触发海量重调度，但底层容量"看似存在实则失联"，形成计算资源的巨大黑洞。Datadog 一边用"活人捞节点"（重启恢复网络）一边应对重调度风暴，各产品按数据链路逐步恢复：实时数据摄入先行，历史数据回填持续到最后。作为监控厂商，Datadog 的宕机让**全球客户在自身故障时失去了眼睛**，其多篇深度复盘（平台层影响、逐产品影响）成为可观测性行业透明度标杆。核心教训：**自动更新就是变更**，必须纳入变更管理——分批、灰度、可暂停。

## 影响评估（CRE 视角）

- **影响面**：US1/US3/US4/EU1/US5 五区域（横跨三大公有云）；指标、日志、APM、RUM、告警全线产品；全球数万客户的监控与告警中断或延迟
- **影响时长**：约 27 小时至全功能恢复（06:03 UTC 3-8 至 08:58 UTC 3-9）；核心摄入链路恢复更早
- **次生影响**：客户在此窗口内自身故障将无告警（监控盲区外溢）；历史数据回填与告警补发的正确性成为客户信任焦点
- **对外沟通评估**：标杆级——状态页高频更新 + CEO 署名复盘 + 平台层/逐产品多篇深度技术复盘
- **定级依据**：多云多区域、全产品、超长时间，SEV-1
- 未披露信息：受影响节点总数（官方称"数万"）、客户告警漏发的量化统计

## 技术细节与根因分析（SRE 视角）

### 背景架构

Datadog 各区域独立部署在 AWS/GCP/Azure 上，底层为大规模 Kubernetes 集群（数万节点），网络层使用 Cilium（eBPF）。节点操作系统为 Ubuntu，一个遗留的无人值守安全更新通道（unattended-upgrades）在基础镜像中处于启用状态——该通道不受 Datadog 常规的分批变更管理控制。

### 因素三分

- **触发因素（Trigger）**：systemd 安全更新经无人值守通道在多区域几乎同时自动应用；systemd 重启过程中与 systemd-networkd/Cilium 的交互清空了节点路由规则，节点网络失联。
- **根本原因（Root Cause）**：自动更新通道游离于变更管理体系之外——无分批、无灰度、无暂停开关，使一个 OS 级变更以"全球同时"的方式落地；基础镜像中该通道的启用状态未被审计发现。
- **扩大因素（Aggravating Factors）**：
  1. 多区域时钟同步的更新窗口让三朵云"同时爆炸"，区域隔离设计被绕过；
  2. 失联节点"看似存在"，Kubernetes 重调度风暴在真实容量塌缩下加剧混乱；
  3. 数万节点的恢复吞吐受限（重启+验证），长尾漫长；
  4. 监控厂商自身宕机=客户集体失明，影响外溢一个行业。
- **减轻因素（Mitigating Factor）**：区域间数据面独立，未发生跨区域数据错乱；摄入链路带缓冲，部分数据可回填。

### 5 Whys

```
现象：三朵云五区域全产品同时受损 27 小时
Why1 → 数万节点网络路由规则被清空，节点集体失联
Why2 → systemd 自动安全更新重启时与网络栈交互清空路由规则
Why3 → 无人值守更新通道在基础镜像中启用，且不受变更管理控制
Why4 → 自动更新未被视为"变更"，无分批/灰度/暂停机制与审计
Why5 → 区域隔离只防了人发起的变更，未防"时间同步触发"的全局变更
        （系统性原因：变更管理边界未覆盖自动化系统自身）
```

## 解决过程

工程师定位自动更新根因后立即全网禁用该通道，通过节点重启批量恢复网络；同时治理 Kubernetes 重调度风暴（限流、优先级排序），按"实时摄入→查询→告警→历史回填"顺序逐产品恢复，27 小时后全功能恢复。整改：清除基础镜像中的无人值守更新通道，所有 OS 更新纳入统一分批变更管理；为"多区域同时故障"场景扩建应急容量与演练；改进大规模节点恢复的自动化吞吐。

## 经验教训

1. **自动更新就是变更**：unattended-upgrades、自动扩缩容、证书自动轮转……任何自动化系统的动作都必须纳入变更管理（分批、灰度、可暂停、可审计）。
2. **"同时性"是区域隔离的天敌**：按时间触发的全局行为（cron、更新窗口）会绕过一切地理隔离——多区域架构必须审计"什么东西会同时发生"。
3. **基础镜像是配置漂移重灾区**：镜像里一个遗留开关潜伏多年，需要常态化的镜像内容审计。
4. **重调度风暴是 K8s 大规模故障的标准并发症**：容量黑洞下的控制面行为需要预设限流与熔断。
5. **监控厂商的故障是行业级事件**：客户需要"监控的监控"（双供应商或自建兜底探测），厂商需要极致透明的复盘来维系信任。

## 预防与改进措施

- **预防（Prevent）**：禁用镜像内自动更新通道，OS 更新统一走分批变更；镜像内容审计常态化
- **减小爆炸半径（Contain）**：更新窗口区域错峰；K8s 重调度限流与优先级控制
- **快速检测（Detect）**：节点网络规则完整性监控；多区域同时异常的聚合告警
- **快速恢复（Recover）**：大规模节点批量恢复工具化；按数据链路分层恢复预案（摄入→查询→告警→回填）
