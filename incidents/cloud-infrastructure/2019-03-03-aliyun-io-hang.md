# 阿里云 3·3（2019-03-03）：华北 2 可用区 C 的 IO HANG——云存储底层的"心肌梗塞"

## 摘要

2019 年 3 月 3 日凌晨，阿里云**华北 2（北京）地域可用区 C** 的部分 **ECS 服务器（弹性计算服务）等实例出现 IO HANG**——磁盘 IO 完全挂起，服务器无法读写数据，犹如"心肌梗塞"。阿里云紧急排查后逐步恢复，并承诺按 SLA 协议赔偿。这是阿里云在 2019 年最严重的故障之一，也是**中国云计算史上第一次大规模 IO HANG 事件**。IO HANG（IO 不响应）是一种特殊的故障模式——服务器操作系统仍在运行，网络连接正常，但磁盘 IO 完全阻塞，导致所有依赖磁盘读写的操作停滞。该故障暴露了阿里云底层存储链路中**内核级缺陷**的风险，以及**单可用区部署架构的脆弱性**。

## 影响评估（CRE 视角）

- **影响面**：华北 2 可用区 C 部分 ECS 服务器及依赖实例出现 IO HANG，大量互联网公司受影响（正值周末，部分用户凌晨发现服务不可用）
- **影响时长**：约凌晨至恢复，约 3 小时（具体恢复时间因实例而异）
- **次生影响**：社交媒体出现大量吐槽，阿里云"宕机"话题登上微博热搜；事故后阿里云承诺按 SLA 赔偿
- **对外沟通评估**：待改进——阿里云在凌晨发布简短公告，确认 IO HANG 问题，但未公布详细技术根因；后续未发布正式技术复盘
- **定级依据**：核心计算服务大面积不可用，影响大量华北区域客户，SEV-1
- 未披露信息：受影响 ECS 实例精确数量、IO HANG 的具体内核版本/缺陷详情

## 技术细节与根因分析（SRE 视角）

### 背景架构

阿里云华北 2（北京）地域可用区 C 是华北区域的核心可用区之一，承载大量互联网公司及企业客户的业务。ECS 服务器依赖底层存储链路进行磁盘 IO 操作，IO HANG 意味着底层存储系统出现异常，导致所有读写请求阻塞。

### 因素三分

- **触发因素（Trigger）**：底层存储链路出现异常，导致部分 ECS 服务器的磁盘 IO 完全挂起（IO HANG）。
- **根本原因（Root Cause）**：阿里云官方未披露详细根因；行业分析认为与**内核级存储驱动缺陷**或**底层存储系统（如盘古/Pangu 分布式存储系统）的元数据异常**有关。IO HANG 的典型原因包括：存储后端不可达、内核存储驱动 deadlock、分布式存储系统的元数据一致性问题。
- **扩大因素（Aggravating Factors）**：
  1. IO HANG 是"无声的故障"——服务器运行正常，但所有 IO 操作卡死，告警系统难以及时发现；
  2. 受影响实例集中在单个可用区，跨可用区冗余部署的客户受影响较小；
  3. 恢复需要重启或迁移实例，耗时较长。
- **减轻因素（Mitigating Factor）**：仅影响华北 2 可用区 C，其他地域及可用区未受影响；阿里云的 SOS 应急响应快速启动。

### 5 Whys

```
现象：华北 2 可用区 C 部分 ECS 服务器 IO HANG
Why1 → 底层存储链路异常，磁盘 IO 完全挂起
Why2 → 存储系统或内核驱动出现缺陷
Why3 → 存储链路的异常处理机制未阻断 IO HANG 的扩散
Why4 → IO HANG 故障模式的检测与隔离能力不足
Why5 → 分布式存储系统的"无声故障"（silent failure）模式
        在测试覆盖中未被充分覆盖
        （系统性原因：IO HANG 类故障的检测与隔离机制不完善）
```

## 解决过程

阿里云工程师紧急排查，定位到 IO HANG 问题后逐步恢复。阿里云官方未披露具体恢复操作（可能是重启实例、迁移或修复存储后端）。事后阿里云承诺按 SLA 协议赔偿，并全面排查其他地域及可用区。

## 经验教训

1. **IO HANG 是"无声的故障"——比"服务器宕机"更难检测**：服务器宕机会触发告警，但 IO HANG 时服务器运行正常、网络正常，只有磁盘 IO 卡死——告警系统需要检测 IO 延迟的异常升高才能发现。
2. **单可用区部署是 IO HANG 的最大受害者**：跨可用区部署的客户可以将流量切换到其他可用区，单可用区部署的客户只能等待恢复。
3. **阿里云在 2019 年的故障透明度仍需提升**：与 AWS/Google 的详细技术复盘相比，阿里云在 IO HANG 事件后未发布正式技术复盘，仅发布简短公告。
4. **"按 SLA 赔偿"是最后的安心剂**：故障发生后，承诺赔偿是维持客户信任的关键——但赔偿金额远低于故障造成的业务损失。

## 预防与改进措施

- **预防（Prevent）**：内核级存储驱动的稳定性测试强化；IO HANG 故障模式的混沌工程演练
- **减小爆炸半径（Contain）**：IO HANG 的自动隔离机制（将受影响实例自动从负载均衡池中移除）；跨可用区冗余部署的最佳实践推广
- **快速检测（Detect）**：IO 延迟异常升高的实时告警；IO HANG 的自动检测（服务器"运行正常但 IO 阻塞"的异常模式识别）
- **快速恢复（Recover）**：受 IO HANG 影响实例的自动迁移机制；存储后端的快速恢复流程

## SRE / CRE / FDE / SA 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | IO HANG 是"无声故障"的典型代表——比"服务器宕机"更难检测，需要 IO 延迟的异常检测而非简单的"进程存活检查"；磁盘 IO 的监控指标（延迟、队列深度、IOPS）应作为核心告警源 |
| CRE | 客户不知道也不关心"IO HANG"是什么——他们只知道"服务器跑着但就是不动了"；故障沟通需要翻译技术术语，让客户理解"我们在修复什么" |
| FDE | IO HANG 的取证需要"存储链路的全路径追踪"——从应用层 IO 请求到内核驱动到存储后端，每一层的日志都需要对齐才能定位根因；IO 延迟的时序数据是判断故障时间点的关键证据 |
| SA（客情危机） | ECS IO HANG 约 3 小时，受影响客户业务停顿；阿里云按 SLA 协议赔偿并公开复盘，但'无声故障'难以检测的特点令客户对监控盲区产生担忧 |
| SA（技术危机） | 单可用区部署是 IO HANG 的最大受害者——客户应跨可用区部署并配置流量切换；IO 延迟异常应纳入监控告警体系，'服务器活着但 IO 卡死'的状态需被检测 |
