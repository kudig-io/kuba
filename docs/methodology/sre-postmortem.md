# SRE 无指责复盘方法（Blameless Postmortem）

本文定义 kuba-database 案例复盘所遵循的 SRE 方法，主要参考 Google SRE Book（Ch.15 Postmortem Culture）及业界通行实践。

## 1. 复盘的目标

复盘不是为了记录"发生了什么"，而是为了回答三个问题：

1. **Why**：系统性缺陷是什么？（不是"谁做错了"）
2. **What if**：哪些防线本可以阻止或缩小影响？
3. **Now what**：哪些改进项可以落地、可被验证？

## 2. 因素三分法

每个案例的根因分析必须区分：

| 类型 | 定义 | 示例（Cloudflare 2019 WAF 故障） |
|---|---|---|
| 触发因素 Trigger | 直接引发故障的事件 | 部署了一条含灾难性回溯的正则规则 |
| 根本原因 Root Cause | 让触发得以造成破坏的系统缺陷 | WAF 规则全球秒级生效、无灰度；正则引擎无 CPU 运行上限 |
| 扩大因素 Aggravating | 延长/放大影响的因素 | 内部系统同样过载，工程师登录受阻 |

> 判别技巧：把 Trigger 换成另一个类似事件，故障是否仍会发生？若会，说明真正的问题在 Root Cause 层。

## 3. 5 Whys 分析

从现象出发连续追问"为什么"，直到抵达组织/流程/架构层面的系统性原因。要求：

- 至少 3 层，通常 5 层；每层答案必须是**可验证的事实**，不是猜测。
- 终点应是"可以被工程手段改变的东西"（流程、防护、架构），而非"人应该更小心"。
- 分支处可拆多条链（一个故障往往有多条因果链）。

```
现象：全球流量下降 82%
Why1 → 边缘节点 CPU 100%，无法处理请求
Why2 → WAF 正则引擎发生灾难性回溯
Why3 → 一条新规则含 .*.*=.* 模式且未被检测
Why4 → 规则类变更走"快速通道"，绕过灰度发布
Why5 → 历史上规则变更被认为"低风险"，流程未随规模演进  ← 系统性原因
```

## 4. 关键时间指标

| 指标 | 定义 |
|---|---|
| **TTD** (Time to Detect) | 故障发生 → 被检测/确认 |
| **TTE** (Time to Engage) | 检测 → 正确的人开始处置 |
| **TTM** (Time to Mitigate) | 故障发生 → 用户影响显著缓解 |
| **TTR** (Time to Resolve) | 故障发生 → 完全恢复 |

案例中尽量还原这四个指标；官方未披露的标注"未披露"，可用公开时间线推算并注明"推算值"。

## 5. 经验教训的书写标准

每条经验教训必须满足 **可迁移 + 可操作**：

- ❌ "变更要更小心" —— 不可操作
- ✅ "任何全球生效的配置类变更必须与代码变更走同等的灰度流程（金丝雀 → 分区域 → 全球）" —— 可直接转化为工程约束

推荐句式：`当 <条件> 时，必须/应当 <工程约束>，否则 <风险>`。

## 6. 预防措施的分层

按防御纵深归类改进项，避免所有措施都堆在"加强测试"：

1. **预防（Prevent）**：让错误无法进入生产（静态检查、变更防护、类型/配置校验）
2. **减小爆炸半径（Contain）**：灰度发布、分区隔离、限流熔断、Cell 架构
3. **快速检测（Detect）**：SLO 告警、变更关联告警、黄金指标
4. **快速恢复（Recover）**：一键回滚、Kill Switch、Break-glass 通道、预案演练
