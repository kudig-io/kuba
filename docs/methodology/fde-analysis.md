# FDE 现场数据工程分析方法（Field Data Engineering）

FDE 视角要求：**复盘的每个结论都能锚定到现场数据（指标、日志、链路、外部观测）**。对公开故障案例而言，"现场数据"包括官方披露的监控截图/数据描述、状态页时间戳、第三方监测（如 ThousandEyes、Downdetector）以及网络公开数据（BGP 路由表、DNS 解析记录）。

## 1. 证据分级

案例中的每个关键事实按证据强度标注来源：

| 级别 | 来源 | 可信度 |
|---|---|---|
| E1 | 官方 Postmortem / RCA 中的数据 | 最高，直接引用 |
| E2 | 官方状态页时间戳、官方博客 | 高 |
| E3 | 可独立验证的公开数据（BGP/DNS 记录、第三方监测图表） | 高，需注明监测方 |
| E4 | 权威媒体/研究者分析 | 中，须标注"第三方分析" |
| E5 | 社区讨论、传闻 | 不采信，仅可作为线索 |

## 2. 时间线重建方法

1. **多源对齐**：官方时间线 + 第三方监测 + 社交信号，统一换算为 UTC。
2. **锚点事件**：以"变更执行时刻"和"指标突变时刻"为主锚点，其余事件相对排列。
3. **缺口标注**：无法确认的时间段显式标注"时间未披露"，禁止编造。
4. **信号滞后分析**：注意缓存类系统（DNS TTL、连接池、租约）造成的"故障延迟显现"——变更时刻与影响时刻的间隔往往就是关键技术细节（如 OpenAI 2024-12 事件中 DNS 缓存延迟了故障暴露）。

## 3. 可观测性缺口分析

FDE 视角的核心产出：**这个故障暴露了哪些"看不见"的问题**。每个案例回答：

- 检测是靠告警、内部巡检，还是客户上报/社交媒体？（后两者即为检测缺口）
- 监控/告警系统本身是否依赖故障组件？（Facebook 2021、Roblox 2021 的共同教训：观测系统与被观测系统循环依赖）
- 是否存在"指标正常但客户受损"的观测盲区？
- 排障过程中缺失了哪类数据导致诊断时间拉长？

## 4. 数据驱动的量化描述规范

- 影响用量化表述替代形容词：❌"大量请求失败" → ✅"错误率从 0.01% 升至 82%（官方披露）"。
- 恢复曲线优于恢复时刻：区分"开始恢复"、"恢复 50%"、"完全恢复"。
- 对未披露数据可给出推算区间并注明方法（如按 Downdetector 报告量衰减推算恢复窗口）。
