# Azure 闰年故障（2012-02-29）：一个日历 bug 击垮了微软的云

## 摘要

2012 年 2 月 29 日约 17:45 PST（2 月 28 日），微软 Azure 的**服务管理功能**在多个区域出现大面积中断，影响 Compute、Access Control Service（ACS）、Service Bus、SQL Azure Portal 等依赖服务，持续时间超过 12 小时。微软事后发布详细复盘确认根因：Azure 的**虚拟机来宾代理（Guest Agent）**在生成 SSL 证书时，**证书有效期的计算逻辑未正确处理闰年 2 月 29 日**——当系统日期为 2012-02-29 时，证书生成代码错误地计算了"当前日期 + 1 年"的偏移量，生成了**无效的 SSL 证书**。该证书被 Azure 管理面的其他组件拒绝，导致服务管理链断裂。这是云计算史上最著名的"**日历 bug（Calendar Bug）**"案例之一，与 Y2K bug 异曲同工——一个看似简单的日期处理问题，在分布式系统的复杂依赖链中被放大为全局故障。

## 影响评估（CRE 视角）

- **影响面**：Azure 服务管理功能在多个区域不可用，影响 Compute、ACS、Service Bus、SQL Azure Portal 等；部分客户虚拟机不可达
- **影响时长**：约 17:45 PST（2/28）起，持续超 12 小时（至 2/29 凌晨~上午）
- **次生影响**：Azure 在 2012 年尚处于与 AWS 竞争的关键阶段，这次闰年 bug 成为 AWS 销售团队对比的经典案例
- **对外沟通评估**：优秀——微软在数日内发布详细复盘博客，含根因、时间线与改进措施，透明度极高
- **定级依据**：多区域核心服务管理功能中断超 12 小时，SEV-1
- 未披露信息：受影响客户数量、Azure 当时的总用户数

## 技术细节与根因分析（SRE 视角）

### 背景架构

Azure 的虚拟机来宾代理（Guest Agent）运行在每个虚拟机中，负责为虚拟机生成 SSL 证书，用于与 Azure 管理面通信。证书有效期的计算逻辑为"当前日期 + 1 年"。当系统日期为 2012-02-29 时，该计算需要处理闰年——但代码未正确处理，生成了无效证书。Azure 管理面的其他组件收到无效证书后拒绝连接，服务管理链断裂。

### 因素三分

- **触发因素（Trigger）**：2012 年 2 月 29 日（闰年）触发 Azure Guest Agent 的证书生成代码中的日期计算 bug。
- **根本原因（Root Cause）**：证书有效期计算逻辑为"当前日期 + 1 年"，但未正确处理闰年 2 月 29 日的情况——代码中硬编码的日期偏移量未考虑 2 月 29 日的特殊性。
- **扩大因素（Aggravating Factors）**：
  1. 无效证书被 Azure 管理面拒绝，导致服务管理链完全断裂；
  2. 多区域同时受影响，无区域隔离机制；
  3. 证书手动重新生成和部署涉及大量虚拟机，恢复时间被拉长。
- **减轻因素（Mitigating Factor）**：已运行的服务（已持有有效证书的虚拟机）继续工作；仅新连接受影响。

### 5 Whys

```
现象：Azure 服务管理功能全局中断超 12 小时
Why1 → 虚拟机来宾代理生成的 SSL 证书无效，被管理面拒绝
Why2 → 证书有效期计算逻辑错误：未正确处理 2 月 29 日
Why3 → 代码中"当前日期 + 1 年"的偏移量未考虑闰年
Why4 → 证书生成代码的测试覆盖未包含闰年场景
Why5 → 分布式系统中一个看似简单的"日期计算"错误，
        在证书→管理→服务的依赖链中被逐级放大
        （系统性原因：日期/时间相关代码的测试覆盖不足 + 证书链路的脆弱性）
```

## 解决过程

修复证书生成逻辑后，手动为各区域重新生成有效证书并部署，服务逐步恢复。微软事后进行了证书生成逻辑的全面审计，增加了闰年、跨年等日期场景的测试覆盖。

## 经验教训

1. **日历/日期 bug 是分布式系统的隐形杀手**：2 月 29 日每 4 年出现一次，但一旦触发，可以在分布式系统中造成全局瘫痪——日期处理代码必须专门测试闰年、跨年、时区边界等场景。
2. **证书链是"信任的脆弱点"**：SSL 证书的生成、分发、验证链路中的任何一处错误，都会导致整个信任链断裂——证书链路的测试应覆盖所有日期边界条件。
3. **12 小时恢复时间暴露了手动恢复的局限**：因需要手动重新生成和部署证书，恢复时间被拉长——证书管理等关键路径应设计自动化恢复机制。
4. **"代码未测试"的 bug 在 4 年一次的触发条件下，找到你只是时间问题**：2008 年 2 月 29 日 Azure 可能尚未上线或未触发该 bug，但 2012 年该来的总会来。

## 预防与改进措施

- **预防（Prevent）**：日期/时间相关代码的全面测试覆盖（闰年、跨年、2 月 29 日）
- **减小爆炸半径（Contain）**：证书生成机制的区域隔离；证书有效性预验证
- **快速检测（Detect）**：证书生成失败/无效的实时告警
- **快速恢复（Recover）**：证书自动重新生成机制；自动化证书部署与验证

## SRE / CRE / FDE / SA 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 日历 bug 4 年触发一次，但一旦触发就是全局故障——"测试覆盖"不应只关注高频路径，低频边界条件往往更致命 |
| CRE | 客户无法理解"闰年 bug"——对他们来说，Azure 就是不可用超 12 小时；技术细节不应成为客户信任修复的借口 |
| FDE | 证书生成失败的取证依赖证书日志与日期计算代码的审计——"代码级别"的根因追溯需要源代码审查，而非仅依赖运行日志 |
| SA（客情危机） | 闰年证书故障致 12 小时服务瘫痪，企业客户对 Azure 的信心受挫；微软事后复盘，但手动恢复耗时暴露恢复能力短板，客户对'低级错误'的容忍度有限 |
| SA（技术危机） | 日期/证书边界 bug 是分布式系统隐形杀手——客户应自建证书到期监控；对平台级'确定会发生'的故障（证书过期、密钥轮转）应有预案与替代通道 |
