# Atlassian 误删事故（2022-04-05）：一个错误的 ID 列表，14 天的漫长恢复

## 摘要

2022 年 4 月 5 日，Atlassian 在执行一次例行维护——停用一个已废弃的旧插件（Insight 独立应用，功能已并入 Jira Service Management）——时发生灾难性误删：负责生成停用目标列表的团队提供的是**站点 ID（site ID）而非应用 ID（app ID）**，而执行团队的脚本以**"永久删除"（permanently delete）模式而非"标记停用"（deactivate）模式**运行。结果 **883 个客户站点（约 775 家客户、双周活跃用户约 40 万）的整个云站点被永久删除**——包括 Jira、Confluence、Opsgenie 等全部产品数据。虽然 Atlassian 拥有完整备份，但其灾备体系是为"整站级故障"设计的：**从共享多租户存储中选择性恢复一小部分客户的数据**没有自动化流程，只能以近乎手工的方式逐站点恢复，前几天每天仅能恢复几十个站点。全部客户恢复历时 **14 天**（4 月 18 日完成）。事故期间沟通严重缺位——许多客户数日内只收到模板化工单回复，CEO 一周后才公开发声。官方 PIR（事后审查）成为 SaaS 行业"删除防护 + 选择性恢复能力 + 危机沟通"三课合一的教材。

## 影响评估（CRE 视角）

- **影响面**：883 个云站点 / 约 775 家客户 / 约 40 万活跃用户，涉及 Jira、Confluence、Opsgenie 等全线产品
- **影响时长**：最长约 14 天（20160 分钟，按最后一批客户恢复计）
- **次生影响**：Opsgenie 被删意味着部分客户的**告警/值班系统消失**——故障管理工具自身故障的嵌套风险；多家客户公开考虑迁移
- **对外沟通评估**：差（事故前 9 天）→ 优秀（PIR 发布后）——初期沟通瘫痪是本案例的第二事故
- **定级依据**：影响客户占比 <0.2% 但数据全删、恢复极长，定 SEV-2（若按单客户视角则为 SEV-1）
- 未披露信息：是否有客户数据最终未能 100% 恢复（官方称全部恢复，个别客户报告边缘数据差异）

## 技术细节与根因分析（SRE 视角）

### 背景架构

Atlassian Cloud 为多租户架构：客户站点数据分散于共享的数据库与存储中。备份体系针对"整库/整服务灾难"设计，支持全量回滚到时间点；但恢复个别租户需要从共享备份中抽取、重建关联关系（跨 Jira/Confluence/身份/权限多系统），当时无自动化工具。删除 API 同时支持"标记停用"（可恢复）与"永久删除"（合规场景用，不可逆）两种模式。

### 因素三分

- **触发因素（Trigger）**：两个团队间的交接错误——需求方给出站点 ID 而非应用 ID，执行方未校验 ID 类型；脚本又被配置为永久删除模式。
- **根本原因（Root Cause）**：大规模删除操作缺乏系统性防护——无 ID 类型/影响面校验、无 dry-run 预演、无分批执行与中途核对、"永久删除"模式无更高审批门槛；同时**选择性恢复能力从未被建设与演练**，把 8 分钟的检测优势变成了 14 天的恢复灾难。
- **扩大因素（Aggravating Factors）**：
  1. 多租户共享存储使单租户恢复=跨系统数据考古，工程量巨大；
  2. 恢复流程边做边建（两套流水线并行迭代），初期吞吐极低；
  3. 客户联系人数据也在被删站点中，Atlassian 一度**找不到该通知谁**；
  4. Opsgenie 同时被删，部分客户失去告警能力，风险外溢。

- **减轻因素（Mitigating Factor）**：Atlassian 最终恢复 883 个客户站点；数据持久性未受根本性损害。

### 5 Whys

```
现象：883 个客户站点被永久删除，恢复历时 14 天
Why1 → 停用脚本以永久删除模式作用在了错误的站点 ID 列表上
Why2 → 跨团队交接未校验 ID 类型；脚本模式选择无审批闸门
Why3 → 大规模删除无 dry-run、无分批、无影响面预演的强制流程
Why4 → 选择性（单租户级）恢复能力缺失，备份只为整站灾难设计
Why5 → 灾备演练只验证过"恢复一切"，从未验证"恢复一部分"
        （系统性原因：删除防护与恢复粒度的双重工程债）
```

## 解决过程

叫停脚本后，Atlassian 组建数百人恢复团队，先以手工流程逐站点恢复（速度极低），同时开发自动化恢复流水线（恢复站点数据、重建跨产品关联、验证一致性、客户确认），恢复吞吐在第二周大幅提升，4 月 18 日全部完成。PIR 承诺的整改：全面推行软删除（soft delete）+ 延迟永久删除、删除类操作的多级审批与 dry-run、建设并常态演练单租户恢复能力（DR 目标加入"恢复粒度"维度）、重建危机沟通流程（备用联系方式、状态页透明度）。

## 经验教训

1. **删除是最高危的操作类别**：任何批量删除必须默认软删除+延迟清理，"永久删除"须专属审批链——本案与 Salesforce 2019、携程 2015 同属"删除防护缺位"谱系。
2. **备份≠恢复能力，恢复粒度是独立维度**：能恢复"全部"不代表能恢复"一部分"；多租户 SaaS 必须建设并演练**单租户时间点恢复**。
3. **TTD 快没用，TTR 才是客户感知**：8 分钟发现、14 天恢复——恢复工程的短板决定事故量级。
4. **跨团队交接是经典错误温床**：ID 类型这种"低级错误"要靠机器校验（类型系统/schema）而不是人的细心。
5. **危机沟通与技术恢复同等重要**：9 天的沟通真空造成的品牌伤害不亚于数据删除本身；备用联系渠道必须独立于产品数据。

## 预防与改进措施

- **预防（Prevent）**：删除脚本强制 dry-run + ID 类型校验 + 分批执行；永久删除模式独立审批链
- **减小爆炸半径（Contain）**：软删除 + 30 天延迟永久清理；批量操作速率限制与中途核对点
- **快速检测（Detect）**：站点消失类不变量监控（本案已达成 8min 检测）
- **快速恢复（Recover）**：单租户时间点恢复流水线常态化演练；客户备用联系方式外置存储
