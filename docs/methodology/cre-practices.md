# CRE 客户可靠性工程实践（Customer Reliability Engineering）

CRE 由 Google 于 2016 年提出，核心思想：**可靠性最终由客户感知定义，而非由系统内部指标定义**。kuba-database 用 CRE 视角评估每个故障的"客户面"，与 SRE 的"系统面"互补。

## 1. 客户感知影响的度量维度

复盘案例时，从以下维度还原客户视角（能获取多少写多少，缺失标注"未披露"）：

| 维度 | 说明 | 示例 |
|---|---|---|
| 影响面 | 受影响客户/用户比例、地域分布 | "全球约 85% 请求报错"（Fastly 2021） |
| 功能维度 | 哪些用户旅程受损：读/写/登录/支付/API | GitHub 2018：网站可读，写入降级 |
| 影响时长 | 客户视角的不可用窗口（≠ 内部完全恢复时间） | |
| 错误预算 | 以 99.9%/99.99% SLO 估算本次事件消耗的年度预算 | 27 分钟全局中断 ≈ 99.99% SLO 五年预算 |
| 长尾影响 | 恢复后的排队、数据回填、缓存击穿等次生影响 | AWS 2021：API 恢复后积压任务处理数小时 |

## 2. 对外沟通评估

CRE 强调"共享命运（Shared Fate）"：故障期间的透明度直接决定客户信任的损耗程度。每个案例评估：

1. **首次通告时延**：故障发生 → 状态页/官方渠道首次确认。
2. **通告质量**：是否说明影响范围、是否给出预估、是否持续更新。
3. **状态页独立性**：状态页是否依赖故障系统本身（AWS 2017 S3 故障中状态页图标存于 S3，是经典反例）。
4. **复盘公开度**：是否发布正式 Postmortem、深度与坦诚程度（GitLab 2017 直播恢复过程是正面典范）。

评级参考：`优秀`（小时级详细复盘+持续更新）/ `良好`（有正式 RCA）/ `一般`（仅状态页简述）/ `不足`（无正式披露）。

## 3. SLO 与错误预算视角

用统一换算评估故障的"预算代价"（按全年计）：

| SLO | 年度不可用预算 | 参考 |
|---|---|---|
| 99.9% | 8h 45m | 一次 4 小时 SEV-1 消耗近半年预算 |
| 99.95% | 4h 22m | |
| 99.99% | 52.6m | 一次 27 分钟全局故障消耗约半年预算 |
| 99.999% | 5.26m | 任何全局 SEV-1 都意味着多年预算透支 |

## 4. 客户侧韧性教训（Consumer-side Lessons）

CRE 视角的独特价值：**从故障中提炼"作为客户/下游该如何自保"**。案例中如适用应包含：

- 多供应商冗余（Dyn 2016 → 多 DNS 提供商）
- 依赖分级与降级预案（Fastly 2021 → CDN 故障时的回源/多 CDN 切换）
- 不把控制面依赖当作数据面依赖（AWS 2021 → 依赖 STS/控制面 API 的系统同样瘫痪）
- 阅读供应商 Postmortem 应成为下游 SRE 的例行工作
