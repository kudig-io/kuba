# Cloudflare 1.1.1.1 中断（2025-07-14）：一个"测试环境"的配置错误，让全球 DNS 解析停摆 62 分钟

## 摘要

2025 年 7 月 14 日 21:48 UTC，Cloudflare 的 **1.1.1.1 DNS 解析器**（全球最受欢迎的公共 DNS 之一）突然从全球互联网消失——BGP 路由被撤消，全球 DNS 解析请求大量失败。Cloudflare 官方博客披露根因：2025 年 6 月 6 日，为预发布（pre-production）的 **Data Localization Suite（DLS）** 服务配置时，**1.1.1.1 的 IP 前缀（1.1.1.0/24 与 1.0.0.0/24）被错误地包含了该服务拓扑中**。此配置变更不是为了生产环境，但在遗留系统中未被校验。7 月 14 日，一个对该预发布 DLS 服务的变更（**添加一个离线数据中心位置**）触发了全局路由配置刷新——系统发现该预发布 DLS 服务包含"离线位置"，将其所有前缀（含 1.1.1.1 等）的 BGP 路由**全部撤消**。故障于 21:52 UTC 生效，工程师在 22:01 收到告警后定位到根因，22:20 回滚今日变更，22:54 所有路由恢复。同时间段内，**Tata Communications** 对 1.0.0.1 的**无关 BGP 劫持**也引发部分关注，但与本次中断无关。该事件是"**配置漂移的延迟引爆**"的经典案例：一个多月前引入的错误配置，在系统拓扑变更时被静默激活，且因遗留系统无法进行灰度发布与阶段性回滚，恢复窗口被拉长。与 Cloudflare 2022-06-21 中断同属"配置级联触发故障"的延续。

## 影响评估（CRE 视角）

- **影响面**：全球使用 1.1.1.1/1.0.0.1 的公共 DNS 解析服务中断约 62 分钟；波及大量个人用户、企业网络、路由器/家庭网关配置
- **影响时长**：21:52-22:54 UTC，约 62 分钟
- **次生影响**：Tata 对 1.0.0.1 的 BGP 劫持（无关事件）使部分观察者误判为"路由劫持攻击"；引发对公共 DNS 解析器单点依赖的讨论
- **对外沟通评估**：优秀——56 小时内发布详细技术复盘（含时间线、根因、BGP 路由图、Tata BGP 劫持的澄清），透明度极高
- **定级依据**：全球核心 DNS 基础设施中断 62 分钟，影响海量终端用户，SEV-1
- 未披露信息：受影响 DNS 查询总量、预发布 DLS 服务的具体变更内容

## 技术细节与根因分析（SRE 视角）

### 背景架构

Cloudflare 的公共 DNS 解析器（1.1.1.1）通过 BGP 将 IP 前缀向全球网络宣告，引导流量到达 Cloudflare 的边缘节点。Data Localization Suite（DLS）是用于满足数据本地化需求的服务拓扑管理工具，其配置管理依赖遗留系统，影响 BGP 路由宣告。

### 因素三分

- **触发因素（Trigger）**：6 月 6 日引入的配置错误（1.1.1.1 前缀被错误纳入预发布 DLS 服务拓扑）在 7 月 14 日该服务拓扑变更时被触发，路由系统将"含离线位置的服务"中所有前缀撤消。
- **根本原因（Root Cause）**：DLS 配置管理的遗留系统允许将生产级 IP 前缀错误地包含在预发布服务拓扑中，且无校验机制拦截；路由系统在拓扑变更时忠实地对"离线"服务执行了路由撤消。
- **扩大因素（Aggravating Factors）**：
  1. 配置错误潜伏 38 天，配置变更审查与系统验证未发现；
  2. 遗留系统不支持灰度发布与阶段性回滚，回滚影响全局；
  3. 预发布服务与生产级 IP 前缀之间缺乏隔离机制。
- **减轻因素（Mitigating Factor）**：告警即时触发，工程师快速定位并回滚。

### 5 Whys

```
现象：1.1.1.1 DNS 解析器全球不可用 62 分钟
Why1 → BGP 路由被撤消，1.1.1.1 前缀从全球网络消失
Why2 → 路由系统对预发布 DLS 服务中"离线位置"执行了路由撤消
Why3 → 1.1.1.1 前缀被错误包含在预发布服务拓扑中（38 天前）
Why4 → 配置管理遗留系统无校验拦截，且无灰度/阶段性回滚能力
Why5 → 预发布环境与生产级 IP 前缀之间缺乏隔离边界
        （系统性原因：混合环境配置隔离缺失 + 遗留系统能力不足）
```

## 解决过程

工程师收到告警后定位到路由异常，22:20 回滚当日变更与 DLS 配置修改，22:54 全球路由恢复。Cloudflare 整改：修复遗留系统配置校验、为预发布/生产环境做 IP 前缀隔离、为路由级配置变更增加灰度发布与阶段性回滚能力。

## 经验教训

1. **混合环境配置隔离是安全底线**：预发布服务的 IP 前缀配置应当无法影响到生产级 IP——像微服务一样，基础设施配置也需要"环境隔离"。
2. **潜伏的配置错误是定时炸弹**：六周前埋下的配置错误，在拓扑变更时爆炸——变更审计应覆盖"被变更影响的所有配置"而非仅"本次变更的配置"。
3. **BGP 路由就是 DNS 解析器的生命线**：公共 DNS 服务依赖 BGP 宣告才能被全球网络访问——路由配置的变更必须按最高风险等级管理，强制灰度。
4. **遗留系统的能力边界就是风险暴露面**：不支持灰度与分阶段回滚的系统，全局故障是其唯一选项——对遗留系统进行"容量评估"时，应包含其"变更引爆半径"。
5. **公共 DNS 解析器的单点属性**：1.1.1.1 故障时，全球海量设备与网络的 DNS 解析退回到备用 DNS 或失败——这是公共基础设施的宿命。

## 预防与改进措施

- **预防（Prevent）**：预发布/生产环境 IP 前缀隔离；配置校验系统拦截生产级 IP 混入非生产拓扑
- **减小爆炸半径（Contain）**：路由级配置变更灰度发布与阶段性回滚；变更影响范围预计算
- **快速检测（Detect）**：BGP 路由撤消的实时告警；DNS 解析器可用性全球探测
- **快速恢复（Recover）**：路由级变更的快速回滚机制；备用 DNS 解析器自动切换预案

## SRE / CRE / FDE 视角速览

| 视角 | 本案例核心结论 |
|---|---|
| SRE | 配置错误潜伏期越长，消灭它的难度越大——变更审计不能只看"本次改了啥"，要算"被改系统影响到了谁" |
| CRE | 公共 DNS 解析器的中断直接让海量终端用户无法上网——公共基础设施的 SLO 应比一般云服务更严格，因为用户没有"切换供应商"的选项 |
| FDE | 38 天前的配置变更是根因，配合 Tata 的无关 BGP 劫持——取证需区分"事故原因"与"同时发生的无关事件"，BGP 数据平面 + RPKI 日志是关键证据源 |
